# CoolHome

Веб-приложение на Go для управления устройствами умного дома Tuya со своего
сервера: список устройств, живые показания, переключатели, слайдеры и
enum-режимы — в одном самодостаточном бинарнике без внешних зависимостей,
сборщиков фронтенда и базы данных.

```
cmd/coolhome        точка входа, флаги, graceful shutdown
internal/tuya       клиент Tuya Cloud OpenAPI: подпись, токен, устройства, команды
internal/home       кэш состояния, валидация команд по thing model, составной провайдер
internal/ir         ИК-пульты как устройства с кнопками (Tuya IR Control)
internal/scene      tap-to-run сцены как кнопки (Scene Linkage Rules)
internal/rules      правила «условие → действие»: движок, хранилище, раннер
internal/dashboard  раскладка пульта: какие контролы показывать
internal/demo       фейковый дом для запуска без credentials
internal/httpapi    JSON API + встроенный дашборд + CORS
web/                шаблон, CSS, JS (embed): app.js + правила в figures.js, power.js
web-tests/          тесты правил интерфейса (node --test)
miniapp/            бандл Tuya MiniApp (tyml/tyss), клиент к этому API
miniapp-tests/      тесты бандла (node --test)
```

## Быстрый старт без ключей Tuya

```bash
make demo          # или: go run ./cmd/coolhome -demo
# http://127.0.0.1:8080
```

В демо-режиме шесть устройств (лампа, розетка, термостат, датчик климата,
шторы, выключенный увлажнитель): команды меняют состояние, датчик «дышит»,
офлайн-устройство отклоняет команды — видно, как ведёт себя интерфейс.

## Подключение своего дома

1. Зарегистрируйтесь на [iot.tuya.com](https://iot.tuya.com) и создайте
   Cloud-проект (**Cloud → Development → Create Cloud Project**).
2. В проекте возьмите **Access ID** (`TUYA_CLIENT_ID`) и **Access Secret**
   (`TUYA_CLIENT_SECRET`).
3. Привяжите аккаунт приложения: **Devices → Link Tuya App Account → Add App
   Account**, отсканируйте QR-код из Smart Life / Tuya Smart (тот аккаунт, где
   уже есть ваши устройства).
4. Убедитесь, что в проекте авторизованы нужные API-сервисы (в терминах Tuya
   это **IoT Core** / **Authorization Token Management** / **Smart Home Device
   Management**; набор зависит от проекта и региона).
5. Выберите дата-центр аккаунта — `TUYA_REGION`:

```
cn    openapi.tuyacn.com            Китай
us    openapi.tuyaus.com            Западная Америка
ueaz  openapi-ueaz.tuyaus.com       Восточная Америка
eu    openapi.tuyaeu.com            Центральная Европа
weaz  openapi-weaz.tuyaeu.com       Западная Европа
in    openapi.tuyain.com            Индия
sg    openapi-sg.iotbing.com        Сингапур
```

Неверный дата-центр выглядит как `sign invalid` / `1004`. Точный хост можно
задать напрямую через `TUYA_BASE_URL`.

6. Запустите:

```bash
cp .env.example .env      # заполните TUYA_CLIENT_ID / TUYA_CLIENT_SECRET / TUYA_REGION
set -a; . ./.env; set +a
make run
```

Файл `.env` приложение не читает само — переменные окружения экспортируйте
любым привычным способом (systemd `EnvironmentFile`, docker `--env-file`, dotenv
в обёртке).

## Конфигурация

- `COOLHOME_ADDR` — адрес прослушивания, по умолчанию `127.0.0.1:8080`.
- `COOLHOME_DEMO` — `true` включает фейковый дом.
- `COOLHOME_AUTH_TOKEN` — если задан, `/api/*` требуют
  `Authorization: Bearer <токен>` (или `X-Auth-Token`).
- `COOLHOME_POLL_INTERVAL` — период опроса облака, по умолчанию `10s`.
- `COOLHOME_DEVICE_IDS` — список `device_id` через запятую, если нужен не весь дом.
- `COOLHOME_CONSOLE_URL` — адрес, на который ведёт ссылка в сообщениях об ошибках,
  требующих действий в консоли Tuya. По умолчанию `https://iot.tuya.com/cloud`;
  принимаются только `http`/`https`.
- `COOLHOME_RULES` — `true` включает движок правил.
- `COOLHOME_RULES_FILE` — файл правил; задание файла включает движок.
- `COOLHOME_RULES_INTERVAL` — период проверки правил; по умолчанию равен периоду
  опроса облака, потому что правило не может увидеть изменение, которого не
  увидел опрос.
- `COOLHOME_TZ` — зона, в которой читается расписание (имя IANA). По умолчанию
  зона машины.
- `COOLHOME_ALLOWED_ORIGINS` — CORS-политика для браузерных клиентов (например,
  Tuya MiniApp в webview): origin через запятую, только `схема://хост[:порт]`,
  без путей. По умолчанию пусто — CORS выключен, заголовки не выставляются.
  `*` открывает API любой странице — используйте только вместе с
  `COOLHOME_AUTH_TOKEN` и осознанно (при старте будет WARN).
- `TUYA_CLIENT_ID`, `TUYA_CLIENT_SECRET`, `TUYA_REGION` — доступ к облаку.
- `TUYA_UID` — uid аккаунта приложения (Smart Life / Tuya Smart), привязанного
  к проекту. Это **не** uid владельца Cloud-проекта, который приходит в ответе
  на токен: `/v1.0/users/{uid}/devices` принимает только uid привязанного
  аккаунта и на чужой отвечает `1106`. Задавать обычно не нужно — при `1106`
  клиент сам находит привязанный аккаунт через
  `/v1.0/iot-01/associated-users/devices` и запоминает uid. Переменная нужна,
  чтобы указать uid явно: тогда он используется как есть и не
  переопределяется.
- `COOLHOME_IR` — `true` включает провайдер инфракрасных пультов: remote'ы,
  сохранённые на ИК-пульте, показываются как устройства с кнопками. Требует
  подписки на сервис **IR Control** в консоли Tuya; без неё приложение работает
  как обычно и пишет одно предупреждение в лог.
- `COOLHOME_IR_BLASTERS` — `device_id` ИК-пультов через запятую. Пусто — найти
  автоматически (категория `wnykq`).
- `COOLHOME_SCENES` — `true` включает провайдер сцен: tap-to-run сцены
  показываются как устройства с одной кнопкой. Это **рабочий способ** нажать то,
  что не умеет data-point API, — сцену исполняет облако Туи.
- `COOLHOME_SPACE_ID` — id дома (`space`). Пусто — определяется автоматически.
- `COOLHOME_DASHBOARD_FILE` — файл с раскладкой пульта (см. ниже). Пусто —
  раскладка только в памяти, изменения не переживут перезапуск.
- `TUYA_BASE_URL` — переопределение endpoint.

Флаги: `-addr`, `-demo`, `-interval`.

## HTTP API

- `GET /api/devices` — снимок дома: устройства, статусы, функции с разобранными
  диапазонами (`min`, `max`, `step`, `scale`, `unit`, `options`).
- `GET /api/devices/{id}` — одно устройство.
- `POST /api/devices/{id}/commands` — запись: `{"commands":[{"code":"switch_1","value":true}]}`.
- `POST /api/refresh` — принудительное обновление из облака.
- `GET /api/health` — состояние синхронизации.
- `GET /api/dashboard` — раскладка экрана:
  `{"widgets":[…],"panel":[…],"names":{…},"descriptions":{…},"hidden":[…],`
  `"groups":[…],"favorites":[…]}` плюс `editable`, `max_widgets`, `max_panel`,
  `max_name_len`, `max_desc_len`, `max_groups`, `max_group_name_len`.
- `PUT /api/dashboard` — сохранить раскладку (`400` при некорректной). Присылать
  можно любой из трёх ключей: отсутствующий список не меняется.

Команда проверяется по thing model устройства: неизвестный код, неверный тип,
значение вне `min..max` или вне `enum` отклоняются с `400` до обращения в облако.
Ошибка облака возвращается как `502` с текстом причины.


## Устройства, которых нет в старом thing model

Часть устройств не описывается старым data-point API: на
`/v1.0/devices/{id}/specifications` облако отвечает `2009 not support this
device`. На вашем доме так было у 12 устройств из 51 — датчик температуры и
влажности, тепловые батареи за шлюзом, сам ИК-пульт.

Оказалось, это не «устройства без модели», а «устройства без **старой** модели».
Тот же аккаунт отдаёт их модель через IoT Core:

```
GET /v2.0/cloud/thing/{id}/model              → {"model": "<json-строка>"}
GET /v2.0/cloud/thing/{id}/shadow/properties  → {"properties":[{"code":"temp_current","value":110}]}
```

Поэтому клиент при `2009` один раз пробует второй эндпоинт
(`internal/tuya/model.go`): если в модели есть что показывать, она переводится в
тот же `tuya.Spec`, что и раньше, а значения берутся из shadow, когда старый
статус пуст. Остальные слои — кэш, валидация команд, API, UI — об этом не знают.

**Запись идёт другим путём.** У этих же устройств старый
`POST /v1.0/devices/{id}/commands` отвечает `2008 command or value not support`
(проверено на «T & H Sensor» и на термостате за шлюзом), а работает запись через
shadow:

```
POST /v2.0/cloud/thing/{id}/shadow/properties/issue
{"properties":{"temp_unit_convert":"c"}}
```

Куда писать, клиент не угадывает по коду ошибки, а знает по факту: `Spec`
запоминает, что устройство описано thing model, и `Command` для такого
устройства идёт в IoT Core. Код `2008` сам по себе означает и «не та поверхность»,
и «недопустимое значение», поэтому по нему одному запрос не переигрывается:
повтор на поверхности, которая не проверяет значения, пропустил бы мусор.
`2009` и `1108` — однозначны, по ним переигровка допустима в любом случае.

Проверено на живом доме: `temp_unit_convert=c` и `mode=socket` (значения, которые
уже стояли, — видимого изменения нет) вернули `200`; `temp_unit_convert=kelvin`
вернул `400` с перечнем допустимых значений, неизвестный код и точка только для
чтения (`temp_current`) — тоже `400`. Почему `400`, а не отказ облака: IoT Core
значения не проверяет (принял `temp_unit_convert=z` при замере), так что thing
model — единственная защита, и проверка идёт до запроса.

**T & H Sensor.** В облаке это устройство записано категорией `tdq`, то есть
«Breaker»: отсюда и `2009` на спеку, и пустой статус. По факту это датчик
температуры и влажности с продуктом `001TH0202_CB3S`:

```
┌──────────────────────────────────────┐
│ T & H Sensor                  ●онлайн │
│ 11.0 °C   ВЛАЖНОСТЬ                   │   ← температура крупно, влажность рядом
│           52 %                        │
│ ⚙ НАСТРОЙКИ                           │   → Батарея «средний» · Единицы °C | °F
└──────────────────────────────────────┘
```

**Что ещё открылось.** «Второй этаж батарея правая стена» и «второй этаж левая
стена» (термостаты за шлюзом) вместо «нет функций» получили 24 функции и 10
показаний каждая. Всего после правки `spec_unsupported` остался у одного
устройства из 62.

**Что по-прежнему не показывается и почему.** Модель есть и у этих устройств, но
показывать её было бы хуже, чем не показывать:

- ИК-пульт (`wnykq`) — в модели только `ir_send` (строка с командой) и
  `ir_study_code` (сырой блоб). Это транспорт, а не функция; его пульты — это
  отдельные устройства, см. **Инфракрасные пульты**.
- RF-выключатели (`rf_switch1`) — в модели `scene_1..4` с единственным значением
  `"scene"`. Это фиксированные команды, а не выбор: четыре кнопки с подписью
  «scene» были бы хуже честного «облако не отдаёт». Управление ими — через
  вкладку «Сценарии» (сцены работают) или с физического пульта.

Правило отбора в `tuya.ParseThingModel`: пропускаются значения типов
`string`/`raw`/`json`/`bitmap` (полезная нагрузка протокола) и enum с менее чем
двумя вариантами. Если после отбора не осталось ни функций, ни показаний,
возвращается исходная ошибка `2009` — и UI по-прежнему объясняет устройство, а не
показывает пустую карточку.

**Кэширование.** Успешная модель кэшируется как обычная спека — 30 минут.
Ответ `2009` остаётся с 24-часовым кэшем, но теперь он означает ровно то, что
означает: у устройства нет ничего, чем можно управлять.

## Инфракрасные пульты

ИК-пульт (`wnykq`) — это отдельная поверхность облака: у него есть remote'ы
(телевизор, кондиционер, гирлянда), а у каждого remote'а — кнопки. Кнопка это
действие, а не состояние, поэтому CoolHome показывает remote как устройство,
у которого все функции — кнопки: запись `true` нажимает кнопку.

Включается через `COOLHOME_IR=true`. Провайдер (`internal/ir`) отдаёт remote'ы в
том же интерфейсе, что и физические устройства, а `home.Multi` склеивает два
провайдера: основной дом и дополнительную поверхность.

```
GET  /v1.0/infrareds/{blaster}/remotes                        библиотечные remote'ы
GET  /v1.0/devices/{blaster}/sub-devices                      выученные remote'ы
GET  /v1.0/infrareds/{blaster}/remotes/{remote_id}/keys       кнопки
GET  /v1.0/infrareds/{blaster}/remotes/{remote_id}/learning-codes  выученные коды
POST /v1.0/infrareds/{blaster}/remotes/{remote_id}/command        нажать библиотечную кнопку
POST /v1.0/infrareds/{blaster}/remotes/{remote_id}/learning-codes передать выученный код
GET  /v1.0/infrareds/{blaster}/categories                     категории
```

**Библиотечные и выученные клавиши — принципиально разные вещи.**

- **библиотечная клавиша** (`standard_key: true`, например `PowerOn` у
  кондиционера) — настоящая кнопка: `POST .../remotes/{id}/command`
  с `{"key":"PowerOn"}`. Работает.
- **выученная клавиша** (`standard_key: false`, все RF-выключатели, у них одна
  клавиша `one_on`) — **облако не передаёт её вообще**. Проверено со всех
  сторон:

  | попытка | ответ облака |
  |---|---|
  | `POST .../command {"key":"one_on"}` | `30706 command or value not support` |
  | `POST .../command {"key":12}` | `30706` |
  | `POST .../learning-codes {"code":"<выученный код>"}` | `success: true`, но в эфир ничего не уходит |
  | `POST .../commands {"code":"ir_send",...}` | `2008 command or value not support` |
  | `PUT .../properties`, `v2.0/cloud/thing/...` | `1108 uri path invalid` |

  Ключевое доказательство по `learning-codes`: запрос возвращает `success`, но
  data point `ir_send` блэстера **не меняется** (его `time` остаётся на дате
  реальной передачи в январе), а `active_time` выключателя не обновляется.
  То есть это «отправить код в режиме обучения», а не рабочая передача.

Поэтому такие клавиши отдаются с типом `Passive`, а не `Button`: устройство
видно, у него перечислены настоящие кнопки, но запись отклоняется с `400` и
объяснением, а в интерфейсе выводится заметка. Кнопка, которая молча не
работает, хуже отсутствующей кнопки.

**Как всё-таки управлять RF-выключателями — через сцены.** Облако не передаёт
выученный RF-код по запросу, но **исполняет сцену**, в которой этот код
записан. Это рабочий путь, и он включён: `COOLHOME_SCENES=true`.

```
GET  /v2.0/cloud/scene/rule?page_no=1&page_size=50&space_id={space}&type=scene
POST /v2.0/cloud/scene/rule/{rule_id}/actions/trigger
```

Сервис называется **Scene Linkage Rules** (старый `Smart Home Scene Linkage`
помечен legacy). Проверено на живом доме: 19 сцен приходят списком, а
`trigger` реально выполняется — облако различает существующую сцену (успех) и
несуществующую (`40003900 No linkage permissions`), то есть вызов доходит до
исполнения.

Две детали этого API:

- **`space_id` обязателен** и берётся только из `/v2.0/cloud/thing/{id}`
  (`bind_space_id`) — в списке `/v1.0/users/{uid}/devices` его нет.
- **Параметры query должны идти по алфавиту**: облако подписывает
  каноническую строку, и другой порядок даёт `1004 sign invalid`. `url.Values.Encode`
  сортирует сам, поэтому клиент корректен.

**Когда сцены включены, RF-выключатели показываются только сценами.**
`COOLHOME_SCENES=true` убирает дубль: и физическую запись `rf_switch1` (у неё нет
data-point модели), и выученный remote из IR-провайдера. Остаётся одна карточка —
сцена, и она работает.

Что при этом **не** скрывается:

- библиотечные пульты (`Кондер` с клавишами `PowerOn`/`T`/…): у них есть рабочие
  кнопки, сцены их не заменяют;
- датчики и сам ИК-пульт: сцены их не покрывают, поэтому они остаются видимыми с
  объяснением, почему через API ничего не отдают.

На типичном доме это 62 устройства вместо 70: 19 сцен, 1 библиотечный пульт,
остальное — физические устройства.

Ограничение: сцена — это действие, а не состояние. CoolHome не знает, включился
ли свет, и одна и та же сцена «вкл/выкл» работает как переключатель.

**Главное открытие: RF-выключатели не видны в `/remotes`.** Они приходят только
как sub-устройства пульта (`/devices/{blaster}/sub-devices`), хотя команды им
отправляются по тому же пути `/remotes/{remote_id}/command`. Провайдер
объединяет оба списка и убирает дубли: без этого восемь RF-выключателей home
показывались как «нет функций». Именно так «Второй этаж», «Лестница»,
«Кухня свет» и остальные получили кнопку.

Две детали этого API стоят отдельного упоминания, потому что обе выглядят как
чужие ошибки:

- **Адресация по `remote_id`, не по `remote_index`.** По индексу облако
  отвечает `1106 permission deny` — выглядит как проблема прав, а на деле
  неверный идентификатор.
- **Ответы — массивы**, а числа в них — строки (`"category_id":"5"`,
  `"remote_index":"449101998"`). Список кнопок завёрнут в объект с `key_list`,
  а `key_id` в реальной библиотеке всегда `0`, поэтому кнопка адресуется
  строкой `key`.

Что важно в поведении:

- **Дополнительная поверхность не ломает основной дом.** Если сервис не
  подписан (облако отвечает `28841101 No permissions. This API is not
  subscribed`), провайдер один раз пишет предупреждение с точной подсказкой,
  где подписаться, и дальше молчит. Список устройств остаётся полным,
  `/api/health` остаётся `ok`.
- **Remote не дублирует своё устройство.** `remote_id` в облаке совпадает с
  `device_id` этого remote'а в списке устройств, поэтому провайдер отдаёт id
  как есть, а составной провайдер заменяет пустую карточку версией с кнопками.
- **Маршрутизация по владению, а не по префиксу.** `home.Multi` запоминает,
  какой провайдер отдал какой `device_id` при последнем опросе, поэтому запрос
  к remote'у не тратится на физический дом и наоборот.
- **Кнопки имеют домен.** Записывать можно только `true` («нажать»); `false`,
  строка или число отклоняются с `400` до обращения в облако — иначе значение
  слайдера ушло бы как нажатие клавиши.
- **Клавиши кэшируются** на 30 минут: они меняются только когда remote правят в
  приложении Tuya. Список пультов ищется один раз за процесс.

Кнопка отрисована и в веб-UI (`.press`, событие `press`), и в бандле MiniApp
(`onPress`).

### Что здесь проверено

Проверено на живом облаке после подписки на IR Control:

- список remote'ов, категорий и sub-устройств разбирается в реальные структуры;
- ключи читаются из `key_list`, а у выученных remote'ов — по одному ключу `one_on`;
- адресация по `remote_index` действительно даёт `1106`, по `remote_id` — работает;
- на несуществующий ключ облако отвечает `30706 command or value not support`
  и для библиотечного remote'а, и для RF-выключателя — то есть путь команды и
  форма тела верны в обоих случаях;
- на реальном доме: 51 устройство, без дублей; «Кондер» — библиотечный remote с
  пятью рабочими кнопками, восемь RF-выключателей — с клавишей `one_on` и
  честной пометкой, что облако их не передаёт.

**Не проверено:** фактическое переключение кондиционера нажатием библиотечной
кнопки — это физическое действие. Путь и форма тела для неё подтверждены
ответом `30706` на несуществующую клавишу (значит запрос доходит и
разбирается).

У RF-выключателя в облаке только один ключ `one_on`: обратного `one_off` нет, и
что именно делает физический пульт (включает или переключает) не сказано нигде
в API. Поэтому подпись кнопки в UI нейтральная — «Кнопка», а не «Включить».

## Tuya MiniApp

В репозитории лежит готовый бандл — каталог [`miniapp/`](miniapp). Это нативный
проект Tuya MiniApp (`tyml`/`tyss`), который подключается к вашему серверу и
работает с домом.

```
miniapp/
  project.tuya.json   имя проекта, baseversion 2.2.0, BaseKit/TYKit/MiniKit
  app.json            страницы, окно, networkTimeout
  theme.json          светлая и тёмная темы через @-переменные
  app.js, app.tyss    точка входа и общие стили
  utils/api.js        транспорт и клиент CoolHome: настройки, /api/*
  utils/format.js     scale и значения: показ и обратное кодирование
  utils/view.js       view-модели: карточка, показания, виджеты
  pages/home/         подключение к серверу и список устройств
  pages/device/       управление: switch, slider, picker, показания
```

Что делает бандл:

- при первом запуске спрашивает адрес сервера и токен и проверяет их через
  `/api/health`; сохраняет в `ty.setStorageSync` только если сервер ответил
  или если он ответил `5xx` — это значит «сервер есть, но его облако не в
  порядке» (неверные ключи, чужой регион, сбой), и такой случай показывается
  баннером на главном экране, а не блокирует сохранение; `401` и сетевые
  ошибки сохранение блокируют;
- список устройств: иконка по категории, превью показаний, отметка «офлайн»,
  pull-to-refresh;
- страница устройства: переключатели для `Boolean`, слайдеры для числовых
  точек с диапазоном, `picker` для `enum`; запись идёт через
  `POST .../commands` с последующей перезагрузкой, поэтому на экране
  оказывается принятое облаком значение, а не нажатие;
- `scale` учтён в обе стороны: сырое `235` показывается как `23.5 °C`, а
  обратно отправляется целым `235` — именно этого требует Tuya;
- точки без диапазона и без `options` не превращаются в виджет, который всё
  равно не сможет отправить значение;
- на офлайн-устройстве команда не отправляется вовсе — показывается
  предупреждение;
- ошибки выводятся текстом: `400` — отказ валидации, `401` — просьба ввести
  токен, `502` — отказ облака или офлайн.

Сборка и запуск:

1. Откройте Tuya MiniApp IDE (Tuya MiniApp Developer Tool).
2. Импортируйте каталог `miniapp/` как проект.
3. Соберите и откройте в симуляторе или в приложении Smart Life.
4. Введите адрес своего CoolHome (публичный HTTPS) и токен доступа.

Проверить логику без IDE можно локально:

```bash
make miniapp-test     # хелперы, клиент и обработчики страниц
make check-all        # то же плюс gofmt/vet/go test
```

Тесты гоняют настоящие страницы и клиент против живого сервера в demo-режиме.
Заглушка `ty` повторяет контракт рантайма (колбеки `request`, синхронный
`storage`), поэтому проверены реальные `onLoad`, `onTap`, `onToggle`,
`onSlide`, `onPick`, а не только чистые функции. Отдельные сценарии со
сбоями (отказ облака, обрыв сети, посторонний сервер по адресу, запись в
полёте) идут на скриптованном рантайме — иначе они зависели бы от того, что
предыдущие тесты сделали с демо-домом.

Каждый такой тест проверен на обратимость: если откатить исправление, он
падает. Это относится и к привязке `disabled` в `tyml` — её читает отдельный
тест по шаблону, потому что JS-тесты шаблон не видят.

### Что должен подтвердить ваш проект

- **Доступ к внешнему домену.** В опубликованных типах рантайма
  (`@tuya-miniapp/api-types`) объявлен только `ty.requestCloud` — прокси к API
  Туи по имени метода, а не произвольный URL. При этом в `app.json` шаблона
  есть `networkTimeout.request`, а рантайм повторяет WeChat-контракт (`ty.*`,
  wx-совместимые вызовы). Сетевой слой бандла изолирован в
  `miniapp/utils/api.js`: он берёт `ty.request`, иначе `wx.request`, и падает
  с понятной ошибкой, если нет ни того, ни другого. Если в вашей консоли
  внешние домены запрещены — добавьте домен CoolHome в allowlist проекта.
- **Origin для CORS.** Если рантайм делает нативный запрос, заголовка `Origin`
  нет и CORS не участвует. Если запрос идёт из webview через fetch, сервер
  должен разрешить этот origin: задайте `COOLHOME_ALLOWED_ORIGINS` (фактический
  Origin видно в логе сервера или в devtools).
- **Публикация.** Панель привязывается к устройству или группе (`deviceId`,
  `groupId` в конфиге инициализации), но бандл показывает *весь дом* с сервера.
  При публикации учитывайте, что пользователь увидит все устройства аккаунта,
  а не только то, для которого открыта панель.

## Пульт на планшете

Интерфейс можно использовать как настенный пульт: открыть на планшете по web и
оставить включённым. Для этого главный экран показывает не все устройства, а
только выбранные контролы.

**Виджет — это контрол, а не карточка устройства.** Один переключатель, один
слайдер, одна кнопка сцены. На стене это удобнее карточек: шесть кнопок нужного
размера вместо шести одинаковых блоков.

### Розетки и выключатели: только состояние

Карточка розетки отвечает на один вопрос — включено или нет:

```
┌──────────────────────┐
│ Smart plug 2    ●онлайн│
│ Включено        [ ██ ] │
│ ⚙ НАСТРОЙКИ            │
└──────────────────────┘
```

Остальные девять контролов — таймер, «состояние после включения», подсветка
кнопки, блокировка, защита от перегрузки, показания счётчика — переехали в окно
настроек. На стене они не нужны, а в карточке занимали четыре экрана прокрутки.

**Какие устройства так сворачиваются.** Те, у которых есть выключатель и нет
того, что на стене крутят: `temp_set`, `bright_value`, `percent_control`,
`colour_data`, `work_mode`, `mode`, `level`. На вашем доме это 16 карточек из 62:
все розетки `cz`, выключатели `tdq` (включая двухклавишное «Уличное освещение»),
счётчики.

**Двухклавишный выключатель** (`smart switch 2ch`) тоже сворачивается, но не в
одну строку, а в две — по одной на клавишу:

```
┌──────────────────────────┐
│ Уличное освещение ●онлайн│
│ Клавиша 1 · Выключено [ ]│
│ Клавиша 2 · Выключено [ ]│
│ ⚙ НАСТРОЙКИ               │
└──────────────────────────┘
```

Клавиши независимы: нажатие переключает только свою. Порядок — как в облаке, то
есть как на физическом корпусе. Таймеры и режимы реле (`countdown_1`,
`relay_status`, `switch_type`) уходят в окно, где подписываются с номером:
«Таймер 1», «Клавиша 2».

**Что осталось с полным набором:**

- лампы и диммеры — яркость и режим нужны на карточке;
- термостаты и обогреватели — уставка температуры;
- гирлянда с цветом — режим и цвет.

### Панель «Сейчас включено»

Над сеткой есть полоса с тем, что включено прямо сейчас: имя устройства и чем
именно оно включено. Из неё видно оставленный свет, не листая карточки; нажатие
на чип открывает настройки этого устройства.

```
СЕЙЧАС ВКЛЮЧЕНО (4)
[ Душевая       ] [ Smart plug 2  ] [ Breaker       ] [ WIFI Meter Pro ]
[ ПИТАНИЕ       ] [ ПИТАНИЕ       ] [ ПИТАНИЕ       ] [ ПИТАНИЕ        ]
```

**Что считается «включено».** Правило узкое: только коды `switch`,
`switch_all`, `switch_led` и `switch_1..n`. Не любой boolean, потому что
настройки тоже boolean, и наивная проверка даёт ложные срабатывания:

- термостаты держат `upper_temp_switch` и `lower_temp_switch` в `true`
  постоянно — это включённые пороговые сигналы, а не питание. На вашем доме
  такая ошибка показала бы четыре окна и тёплых пола включёнными, хотя они
  выключены;
- у розеток есть `child_lock` и `overcharge_switch`, у Breaker —
  `switch_prepayment`, у увлажнителей — `muffling`.

Правило лежит в `web/static/power.js` и покрыто тестами (`make web-test`),
потому что ошибка здесь не косметическая: панель начала бы утверждать, что
устройство работает.

**Общий выключатель главнее реле.** У «Душевой» облако одновременно отдаёт
`switch_all = false` и `switch_1 = true`. Первая версия правила брала любой
включённый `switch_N` и показывала устройство включённым, а в настройках первый
же контрол — «Питание (всё)» — был выключен. Теперь приоритет такой:

1. есть `switch_all` — он и решает;
2. иначе есть `switch` — он;
3. иначе `switch_led`;
4. иначе независимые реле `switch_1..n`, и тогда «включено», если горит хотя бы
   одно — это верно для удлинителя без общего выключателя.

На вашем доме правило убрало из панели ещё одно устройство: было 4, стало 3.

**Офлайн-устройства не показываются.** Если устройство потеряло связь, его
последнее известное состояние может быть устаревшим: розетка могла обесточиться
вместе с роутером, и «вкл» в облаке ничего не значит. Панель отвечает на вопрос
«что работает сейчас», поэтому в неё попадают только устройства на связи.
На вашем доме это убрало два чипа из шести.

**Сцены не попадают в панель.** Сцена — действие, а не состояние: у неё нет
«включена». Придумывать её статус значило бы врать.

Панель скрыта, когда ничего не включено, и в режиме правки, где она только
мешает.

### Две вкладки: устройства и сценарии

Сцены — действия, а не устройства: у них нет состояния, и в общем списке они
мешали искать свет. Поэтому главный экран разделён на две вкладки —
«Устройства» и «Сценарии», — и сцена попадает только во вторую.

Переключатель стоит **в шапке, рядом с «Обновить»**. Сначала он был полосой под
панелью «Сейчас включено», но там он уезжал вверх при прокрутке: на планшете
переключиться можно было, только вернувшись к началу страницы. Шапка же
прилипает к верху, и переключатель виден всегда.

Шапка на планшете выглядит так — переключатель стоит между временем
обновления и действиями:

```
CoolHome   ·   Обновлено в 22:45   [ Устройства | Сценарии ]   Обновить
```

Что стоит знать:

- Выбранная вкладка пишется в адрес (`?tab=scenes`), поэтому перезагрузка
  возвращает на ту же вкладку, а закладка на планшете может открывать сразу
  сцены.
- Карточка сцены — заголовок, подпись «Сценарий» и одна кнопка «Запустить»:
  повторять название на кнопке незачем, она и так под ним. Нажатие отправляет
  `{"code":"trigger","value":true}`; оптимистичного состояния нет, показывать
  нечего.
- Сцена, выключенная в приложении Tuya, приходит как офлайн-устройство с
  объяснением, а не как кнопка, которая молча не сработает.
- Правка пульта живёт на вкладке устройств: уход на «Сценарии» завершает режим
  редактирования, чтобы он не остался висеть наполовину.
- Клавиатура работает: Enter или пробел на карточке запускают сцену.

### Описание сценария

У сцены нет настроек: её единственный контрол — кнопка «Запустить», и она уже на
карточке. Ссылка «Настройки» вела в окно, где не было ничего, кроме копии этой
кнопки, — тупик, который читался как сломанная карточка. Поэтому её убрали, а на
карточке появилось **описание**: поле, где написано, что сцена делает на самом
деле.

```
┌────────────────────────────────┐
│ главный свет вкл/выкл   ●онлайн │
│ Сценарий                        │
│ [        Запустить          ]   │
│ Выключает свет в зале           │
│ и на кухне                      │
│ ✎ Описание                      │
└────────────────────────────────┘
```

Имя сцены говорит, как она называется; описание — какие лампы она трогает. Это
локальная заметка, как и локальное имя: **в облако она не уходит** и в приложении
Tuya её нет. Хранится в том же файле, что раскладка, в поле `descriptions`,
ключ — id сцены; предел — 280 символов, переводы строк сохраняются.

Редактирование — кнопка **✎ Описание** (или **＋ Описание**, если текста ещё
нет) прямо на карточке. Окно то же, что у переименования: имя и описание
сохраняются **одним запросом**, чтобы сбой не оставил новое имя со старым
описанием.

### Скрыть сцену вместо удаления

Сцену, сделанную в приложении Tuya, через API **не удалить** (см. ниже), а список
из двадцати сцен, где четыре давно мертвы, — это список, который никто не читает.
Поэтому сцену можно **скрыть**: локально, без единого запроса в облако и без
потери самой сцены — из приложения она продолжает работать.

На карточке рядом с «Описание» есть **⌣ Скрыть**. Скрытая сцена уходит из списка,
а над списком появляется строка «Скрыто: N» и кнопка **«Показать скрытые»**:
скрытое показывается приглушённым, с пометкой «скрыт» и кнопкой **↩ Показать**.
Вернуть сцену — одно нажатие, и это важно: скрытие не должно быть ловушкой.

- Скрытие **сохраняется на сервере**, как раскладка и имена: скрытое на планшете
  скрыто и на телефоне, потому что это решение про дом, а не про экран.
- «Показать скрытые» — наоборот, **не запоминается**: это разовый просмотр, и
  планшет на стене, открыв страницу заново, снова должен показывать короткий
  список.
- Если скрыты все сцены, список не выглядит пустым домом: страница пишет, что
  все сценарии скрыты, и предлагает их показать.
- В облако при этом **не уходит ничего**: сцена остаётся включённой и срабатывает
  из приложения и из правил CoolHome. Скрытие — только про отображение.

Хранится в том же файле раскладки, поле `hidden` — список `device_id`. Предел
200 записей, дубликаты отклоняются. В интерфейсе кнопка есть только у сцен:
скрывать произвольные устройства незачем, у них есть пульт и панель.

### Редактор сцен

На вкладке «Сценарии» есть **＋ Сценарий** и **✎ Изменить** на каждой карточке.
Редактор пишет в облако Tuya — сцена появится и в приложении, — и проверяет
действия до отправки.

```
┌ Сценарий ─────────────────────────────────┐
│ Название  [ Вечерний свет              ] │
│ Что делает                                │
│  [Лампа ▾] [Питание ▾] [true]  ✕          │
│  ＋ действие                              │
│  Значение: true или false.                │
└───────────────────────────────────────────┘
```

Действие — это устройство, его функция и значение. Список функций берётся из
thing model устройства, поэтому выбрать «то, чего у лампы нет» нельзя, а
**значение проверяется той же функцией, что и нажатие на карточке**: тип, диапазон
`min..max` и допустимые варианты enum. Сцена, которая записала бы значение вне
диапазона, была бы принята облаком и сломалась ночью, когда никто не смотрит.

**Что редактор сохраняет, а что нет.** Облачная сцена может содержать действия,
которые CoolHome не строит, — нажатие ИК-кнопки пульта (`ir_issue_vii`). Такие
действия показываются в окне серым списком и **сохраняются как есть**: обновление
отправляет прочитанный документ целиком, заменив только имя и действия устройств.
Иначе правка имени у сцены с ИК-кнопкой молча выбросила бы кнопку.

Порядок действий — часть смысла сцены, поэтому новые действия встают в те места,
где были старые, а ИК-действия остаются на своих позициях.

**Сцену без своих действий можно переименовать.** На доме, где это писалось, у
семи сцен из девятнадцати все действия — ИК-кнопки пульта или запуск другого
правила (`rule_trigger`). Редактор таких действий не строит, но и не мешает:
список показывается текстом, кнопки «＋ действие» рядом, а сохранить новое имя
можно — действия уходят в облако нетронутыми. Пустым список действий стать не
может: облако отвечает на это `actions param is empty`, и CoolHome проверяет то
же самое до отправки.

**Сцены, которые нельзя изменить.** На часть сцен облако отвечает
`40003007 This rule contains data that is currently not supported for querying`:
их можно запускать, но не прочитать. Такую сцену редактор не открывает — вместо
формы показывается окно с объяснением и ссылкой в консоль Tuya. Открыть форму и
записать «что получилось» было бы догадкой о содержимом.

**Удаления нет.** Сцены, созданные здесь, удаляются только в приложении Tuya (см.
ниже); скрыть их можно кнопкой на карточке.

### Что умеет API сцен

Проверено запросами к живому проекту, не по документации:

- **Список** — `GET /v2.0/cloud/scene/rule?space_id=…&type=scene&page_no=1&page_size=50`.
  Работает, так CoolHome и получает сцены.
- **Одна сцена** — `GET /v2.0/cloud/scene/rule/{id}`. Отвечает действиями и
  условиями: `{"actions":[{"action_executor":"ir_issue_vii","entity_id":"…",
  "executor_property":{"function_code":"keyId","function_value":"12"}}],
  "conditions":[],"name":"…","status":"enable","type":"scene"}`. Часть сцен
  отвечает `40003007 This rule contains data that is currently not supported for
  querying` — читается не всё.
- **Запуск** — `POST /v2.0/cloud/scene/rule/{id}/actions/trigger`. Работает, это
  кнопка «Запустить».
- **Создание** — `POST /v2.0/cloud/scene/rule`. Маршрут есть: с пустым телом
  облако отвечает `40003001 space_id param is empty`, дальше по одному требует
  `name`, `type`, `actions`. Значит сцена создаётся этим запросом.
- **Правка** — `PUT /v2.0/cloud/scene/rule/{id}`. Маршрут тоже есть: на
  несуществующий id приходит `1109 param is illegal`, тогда как на выдуманный
  путь — `1108 uri path invalid`. То есть облако разобрало адрес и проверило
  параметры.
- **Удаление** — здесь два разных ответа, и разница важна:
  - `DELETE /v2.0/cloud/scene/rule/{id}` отвечает `1108 uri path invalid`:
    удаления по одному id нет. Проверено с id, которого заведомо нет в списке
    сцен, и с выдуманным подпутём — оба раза `1108`.
  - `DELETE /v2.0/cloud/scene/rule` (**коллекция**) отвечает
    `40003900 No linkage permissions` — при любом теле, включая пустое, только
    `space_id` и корректный `rule_ids`. Это **не** «нет пути»: контрольный опыт
    с тем же методом на выдуманном пути даёт `1108`, а здесь облако разобрало
    маршрут и отказало по правам. То есть маршрут удаления есть, но проект не
    имеет прав на управление сценами.
- Старый сервис `/v1.0/iot-03/scenes` в этом проекте не подписан
  (`28841106 No permissions`), так что сцены доступны только через текущий
  Scene Linkage Rules.

**Права — единственное, что отделяет удаление от нас.** `40003900 No linkage
permissions` — это отказ по авторизации, а не по формату запроса: формат облако
проверяет отдельно (`1109 param is illegal` на несуществующий id при `PUT`,
`40003001 space_id param is empty` при создании). Значит удаление, скорее всего,
заработает, если в консоли Tuya у проекта появится авторизация на управление
сценами (сервис Scene Linkage и права привязанного аккаунта на изменение
сценариев, а не только на их запуск). Проверять это на настоящей сцене я не
стал: удаление необратимо, а откатить его через API нельзя — второго маршрута,
который бы вернул сцену, нет.

**Чего я не делал.** Сцену на вашем аккаунте я не создавал, не менял и не
удалял: это изменило бы данные в облаке, а откатить сцену через API нельзя —
восстановить её было бы нечем. Поэтому «создание и правка работают» — вывод из
ответов облака на заведомо неполные запросы, а не из завершённого цикла.
Полноценный редактор сцен в CoolHome не сделан: локального описания достаточно,
чтобы понять, что сцена делает, а правка самой сцены — отдельная задача со своим
риском.

**Про «выключить сцену» в облаке.** Отдельного маршрута для статуса я не нашёл, но
`PUT /v2.0/cloud/scene/rule/{id}` читает параметры (`1109 param is illegal` на
пустое тело) — то есть правка возможна, если тело полное. Проверять это на вашей
сцене я не стал: частичное тело могло бы переписать автоматику, а вернуть прежнюю
версию нечем. Поэтому «выключить сцену в облаке» пока не сделано, а скрытие —
сделано, и оно ничего не ломает.

### Как настроить

Всё делается на главном экране, без отдельной страницы настроек.

Кнопки «Изменить» в шапке больше нет: после появления групп она правила не то,
что обещала — заменяла сетку виджетами. Правка панели переехала в саму панель
(см. ниже), а редактор пульта остался доступен по закладке, потому что настраивают
пульт один раз и обычно на настенном планшете, где адресную строку не достать:

1. Открыть `http://<сервер>:8080/?edit=1` — сетка становится редактором пульта.
2. Добавить контрол: тайл **＋ Добавить** в конце сетки → выбрать из списка →
   контрол сразу появляется на пульте.
3. Убрать: **✕** под карточкой. Порядок: **←** и **→**. Ширина: **1×/2×**.
4. Убрать `?edit=1` из адреса (или перезагрузить страницу) — правка закончена.

Пока настроен пульт, сетка показывает виджеты, и полоса групп скрыта: фильтровать
там нечего. Панель при этом работает как обычно.

**Сохранение происходит сразу после каждого действия** — кнопки «Сохранить»
нет. На настенном планшете нет момента «я закончил»: человек нажимает ✕ и уходит,
и ожидает, что так и останется. Запрос уходит с задержкой 250 мс, чтобы серия
быстрых нажатий не превращалась в очередь запросов.

Пока раскладка пуста, показываются все устройства, как раньше, — существующая
установка продолжает работать без настройки. Убрать последний контрол тоже
безопасно: пульт снова превращается в общий список.

Пока идёт правка, органы управления внутри карточек не реагируют на нажатия:
иначе промах мимо **✕** переключил бы свет.

### Группы устройств

Главный экран — полоса вкладок над сеткой. Первая — **«Избранное»**, и она
открывается по умолчанию: планшет на стене открывают, чтобы нажать привычное, а
не чтобы пролистать сорок три карточки.

```
 ┌ Избранное 2 ┐ ┌ Свет 2 ┐ ┌ Климат 0 ┐ ┌ Все устройства 43 ┐    ＋ Группа  ✎ ✕
```

- **Группа** — это набор устройств с именем и порядком. Устройство состоит не
  более чем в одной группе: «перенести в группу» — это перенос, а не копия. Две
  вкладки с одной карточкой были бы двумя местами, откуда её менять, и после
  обновления они могли бы разойтись.
- **Избранное** — наоборот, сквозной список: устройство может быть в избранном и
  одновременно в группе. Смысл именно в этом — «что я нажимаю каждый день» не
  место, где устройство живёт, а второй взгляд на устройства, которые живут в
  группах.
- **«Все устройства»** всегда последняя и всегда есть. Устройство, не попавшее ни
  в одну группу, находится там; полоса вкладок, которая может спрятать
  устройство, хуже, чем никаких вкладок.
- **Создать:** «＋ Группа» в полосе — одно поле и кнопка. Новая вкладка сразу
  открывается: создать пустую группу и остаться на прежней — это без обратной
  связи.
- **Перенести устройство:** «Настройки» на карточке → поле **«Группа»**. Одна
  карточка — один адрес, работает и с телефона.
- **В избранное:** там же кнопка **☆ В избранное**. Выбранное открывается первым
  после любой перезагрузки.
- **Переименовать и удалить** группу — ✎ и ✕ справа в полосе, для выбранной
  вкладки. Удаление группы **не удаляет устройства**: они перестают быть в
  группе и остаются в доме, на вкладке «Все устройства». Об этом сказано и в
  подтверждении.
- Пустая вкладка пишет, почему пуста и что делать, а не выглядит сломанной.

Вкладки — часть экрана устройств: при настроенном пульте сетка показывает
виджеты, и полоса групп скрывается, потому что фильтровать там нечего.

Хранится в файле раскладки, поля `groups` и `favorites`; в облако не уходит
ничего. Названия групп уникальны без учёта регистра («Свет» и «свет» — не две
вкладки, а загадка), предел — 12 групп и 40 позиций в избранном. Правила отбора и
переноса живут в `web/static/groups.js` и покрыты тестами: ошибка здесь тихая —
устройство, выпавшее из последней группы, просто исчезает со страницы.

### Левая панель

Экран разделён на две части: панель слева и основную область справа. В панель
кладут **целые карточки устройств** — не отдельные контролы, как на пульт, а всю
карточку с её переключателями, слайдерами и «Настройками». Это разное назначение:
пульт — то, что нажимают, панель — то, что хотят видеть, не ища.

```
┌──────────────────┬───────────────────────────────────────┐
│  ПАНЕЛЬ      3   │  Свет в гостиной    Кофемашина        │
│  Термостат       │  [ ██ ]             [   ]             │
│  21.4 °C         │                                       │
│                  │  Датчик климата                       │
│  Датчик климата  │  23.1 °C  ВЛАЖНОСТЬ 41 %              │
│  23.1 °C  41 %   │                                       │
└──────────────────┴───────────────────────────────────────┘
```

- **Кнопка «Изменить» живёт в самой панели**, рядом с её заголовком, и правит
  только её: добавить, убрать, переставить. Сетка и группы при этом не меняются.
- **Добавить:** «Изменить» в панели → «＋ Добавить» → выбрать устройство. Список
  показывает устройства, которых в панели ещё нет; сцены в него не попадают —
  сцена это действие, а панель отвечает на вопрос «что сейчас дома».
- **Убрать:** **✕** под карточкой в панели. **Порядок:** **↑** и **↓** — панель
  вертикальная, поэтому стрелки вверх-вниз.
- Предел — 12 карточек. Это не произвольное число: карточка занимает несколько
  строк, и больше дюжины уже не «видно с одного взгляда», а длинная прокрутка.
- Панель видна на обеих вкладках: это часть экрана, а не вкладки «Устройства».
- Пустая панель не занимает места — колонка не появляется вовсе, а кнопка
  «Изменить» была бы недостижима. Поэтому, пока панели нет, в полосе групп
  появляется **＋ Панель**: он открывает пустую колонку в режиме правки. Как
  только в панели есть карточка, кнопка живёт только в самой панели.
- Устройство исчезло из дома — карточка остаётся на месте с пояснением. Тихо
  выбрасывать её нельзя: панель перестроилась бы под рукой, тянущейся к карточке.
- Управление внутри карточки панели работает так же, как в сетке: те же
  обработчики подписаны на оба контейнера, поэтому переключатель, слайдер и
  «Настройки» шлют те же команды.
- Одна и та же карточка может быть видна дважды — в сетке и в панели. Поэтому у
  слайдера нет `id`, а цифра рядом с ним ищется от самого слайдера
  (`input.closest('.row--slider')`): глобальный `getElementById` вернул бы первую
  копию в документе, и, потянув слайдер в панели, вы увидели бы, как меняется
  число в другой колонке.
- Пока идёт правка, карточка в панели **инертна** (`inert`, плюс
  `pointer-events: none` для старых WebView): под ней стоят ↑/↓/✕, и промах мимо
  крестика не должен включать свет. В сетке то же правило работает иначе — при
  правке её карточки заменяются редактором, и нажимать там нечего.
- Отступ липкой колонки считается от **измеренной** высоты шапки (`--header-h`,
  `ResizeObserver`): бейдж «демо» или длинное время обновления переносят шапку на
  вторую строку, и фиксированное число спрятало бы заголовок панели под ней.
- Кнопки правки называют устройство в `aria-label` («Термостат на кухне: ниже»), а
  не просто «Ниже»: в колонке из двенадцати карточек двенадцать одинаковых меток
  бесполезны. Фокус после ↑/↓/✕ возвращается на ту же кнопку, поэтому
  переупорядочивание с клавиатуры не требует заново идти табом с начала страницы.
- На широком экране (от 1024 px) панель — отдельная липкая колонка слева: она
  остаётся на месте, пока основная часть прокручивается. На телефоне она уходит
  под основную часть и растягивается на всю ширину: к телефону подходят за
  устройствами, и колонка карточек над ними только отодвинула бы их вниз.
- В разметке панель стоит **первой**, и на широком экране порядок обхода с
  клавиатуры и скринридером совпадает с тем, что видно. На узком экране
  визуальный порядок переворачивается (`order`), потому что устройства важнее;
  это осознанный размен — на телефоне клавиатурой не пользуются.
- Панель и сетка центрируются как одна композиция (`max-width: 1280px + 20rem`),
  иначе на широком мониторе панель прилипла бы к краю окна, а сетка стояла
  по центру, с полосой пустого фона между ними.
- Линия между колонками — `border-left` основной области, а не `border-right`
  панели: панель по высоте равна своим карточкам (она липкая и прокручивается
  отдельно), и граница на ней обрывалась бы посреди страницы.

### Локальные имена устройств

Устройство можно назвать по-своему — **только здесь**. В облаке и в приложении
Tuya имя остаётся прежним: Tuya такого API не даёт, и CoolHome его не изобретает.
Локальное имя живёт в том же файле, что раскладка, и применяется, когда сервер
отдаёт устройства, — поэтому его видят и карточки, и панель, и пульт, и чипы
«Сейчас включено», и мини-апп.

```
┌─────────────────────────────────────┐
│ Название: Климат в спальне          │
│ ┌─────────────────────────────────┐ │
│ │ Климат в спальне                │ │
│ └─────────────────────────────────┘ │
│ Так устройство называется только    │
│ здесь. В облаке и в приложении Tuya │
│ имя не меняется.                    │
│  [Вернуть имя из облака]  Отмена  Сохранить │
└─────────────────────────────────────┘
```

Как попасть:

- **с карточки** — «Настройки» → **✎ Переименовать**. Кнопка «Настройки» теперь
  есть у каждой карточки, а не только у сенсоров и розеток: иначе у устройства,
  все контролы которого помещаются на карточке, не было бы входа вовсе;
- **с пульта** — **⚙** в правом верхнем углу виджета. Настроенный пульт заменяет
  собой сетку устройств, и без этой кнопки единственным способом добраться до
  настроек было бы стереть пульт.

Что стоит знать:

- **Пустое поле — это сброс.** Стереть имя и сохранить — то же, что «Вернуть имя
  из облака»; набранное облачное имя тоже не сохраняется как переименование.
- **Предел — 60 символов**, тот же, что у подписи виджета, и оба считаются в
  **символах (рунах), а не в байтах**. Это не придирка: в кириллице две буквы на
  байт, и подсчёт по байтам ограничил бы русское имя вдвое сильнее английского —
  в интерфейсе, который весь по-русски. Нашлось на живом прогоне: имя из 30 букв
  проходило, а подпись виджета «Кухонный светильник над столом · Таймер» (39
  символов, 73 байта) отклонялась, и вместе с ней терялось всё переименование,
  потому что имя и подписи уходят одним запросом.
- **Подпись виджета обрезается под предел.** Имя в 60 символов плюс «· Таймер»
  уже не помещается, поэтому при переименовании имя укорачивается до того, что
  осталось после суффикса, — иначе суффикс (название контрола) съедался бы первым.
- **Виджеты на пульте переименовываются вместе с устройством.** Подпись виджета
  фиксируется, когда контрол добавлен на пульт, поэтому без этого на стене
  осталось бы старое имя на кнопке и новое на карточке рядом. Переименование
  трогает только те подписи, которые были **выведены** из имени устройства
  («Кофемашина» и «Кофемашина · Таймер»); подпись, набранную вручную, оно не
  переписывает — это был бы выбор пользователя, а не копия имени.
- **Облачное имя никуда не девается.** Когда устройство переименовано, API отдаёт
  и локальное `name`, и исходное `cloud_name` — по нему работает «Вернуть имя из
  облака».
- **Отдельное окно, а не поле в настройках.** Настройки перерисовываются каждые
  восемь секунд вместе с данными; поле внутри них теряло бы набранное на полуслове.
- **Имена — это локальные данные, а не команда.** Ни один запрос к Tuya при
  переименовании не уходит: `internal/tuya` не знает о переименовании вовсе.
- **Имя и подписи уходят одним запросом.** Двумя пришлось бы платить: если бы
  второй упал, на стене осталась бы старая подпись при новом имени.
- **Сохранение раскладки стало атомарным.** `PUT` применяет изменение под одной
  блокировкой (`Store.Update`), поэтому телефон, добавивший карточку в панель, и
  планшет, переставивший виджеты, больше не затирают друг друга: раньше каждый
  читал раскладку, правил свою часть и записывал целиком.

### Где хранится

На сервере, в файле `COOLHOME_DASHBOARD_FILE`:

```json
{
  "widgets": [
    { "device_id": "bf6ea99d…", "code": "switch_led", "title": "Свет", "span": 2 },
    { "device_id": "W00cRSrGbI8uKzrj", "code": "trigger", "title": "Кухня" }
  ],
  "panel": ["bfa33762…", "bfb7dccc…"]
}
```

- `title` — подпись на пульте (иначе берётся имя устройства);
- `span` — `1` или `2` колонки;
- порядок в массиве = порядок на экране;
- `names` — локальные имена устройств: `{"device_id": "Имя"}`. Ключа может не
  быть; пустое имя не хранится (это сброс к облачному);
- `descriptions` — локальные описания: `{"device_id": "Что делает"}`. Пустое
  описание не хранится;
- `groups` — вкладки главного экрана: `[{"id":"g1","name":"Свет","devices":["…"]}]`;
- `favorites` — избранное: `["device_id", …]`, сквозной список, не группа;
- `hidden` — локально скрытые: `["device_id", …]`. Пустой список показывает всё;
- `panel` — устройства в левой панели, по одному `device_id` на карточку. Ключа
  может не быть: файл, записанный до появления панели, читается как пульт с
  пустой панелью.

В `PUT` отсутствие ключа означает «не трогать этот список», а `"panel": []` —
«очистить». Страница отправляет только то, что изменилось: правка пульта шлёт
`widgets`, правка панели — `panel`. Это не педантизм: пульт и панель правятся из
разных мест, часто с разных устройств, и телефон, добавивший карточку в панель,
не должен обнаружить её пропавшей после того, как планшет переставил виджеты.
Запрос без обоих ключей отклоняется с `400`.

Почему не `localStorage`: планшет на стене теряет кэш при обновлении браузера или
замене железа, и вместе с ним уехал бы весь пульт. Файл переживает и это, и
перезапуск сервера. Заодно один набор видят планшет и телефон.

Файл пишется атомарно (временный файл + `rename`), так что сбой посреди записи не
оставит обрезанный JSON. Раскладка читается и пишется через
`GET`/`PUT /api/dashboard`; сервер проверяет её (уникальность, обязательные поля,
пределы 200 виджетов и 12 карточек панели) и отвечает `400` с объяснением.

### Батарея: карточка предупреждает заранее

Датчик с севшей батареей замечают, когда он перестаёт отвечать. Поэтому карточка
говорит об этом заранее: рамка и полоска слева окрашены, рядом с состоянием —
значок с зарядом.

```
┌────────────────────────────────────┐
│ 1 floor temperature   ●онлайн  🔋10 %│  ← рамка красная: менять батарею
│ WiFi Temperature and Humidity Sensor│
│ 11.1 °C        ВЛАЖНОСТЬ 49 %      │
└────────────────────────────────────┘
```

- **красная** рамка — `battery_state: low` или ≤ 15 %: «почти разряжена,
  замените»;
- **янтарная** — `middle` или ≤ 40 %: «разряжается»;
- **здоровый заряд не окрашивается вовсе**. Страница, где все карточки цветные,
  не говорит ничего; смысл подсветки в том, что она редкая. Заряд виден в
  «Настройках» у любой карточки.

**Две кодировки, одно правило.** Tuya отдаёт батарею двумя способами, и на вашем
доме встречаются оба: `battery_state` (`low`/`middle`/`high`) и
`battery_percentage` (0…100). Где есть `battery_state`, решает **он**: это
суждение самого устройства, сделанное прошивкой, которая знает элемент. Проценты
— запасной вариант. Порог процентов (15 и 40) — **наш выбор, а не факт из
облака**: облако не говорит, где начинается «низкий». Выбрано так, чтобы дымовой
датчик на 28 % уже был отмечен; порог записан в `web/static/battery.js`
константами, и его можно оспорить.

Устройство без батареи не получает ничего; нечисловой или небывалый процент
(больше 100, отрицательный) игнорируется, а не красит карточку наугад;
неизвестное значение enum не угадывается — если процентов нет, карточка остаётся
нейтральной.

Правило отбора живёт в `web/static/battery.js` и покрыто тестами
(`make web-test`), потому что ошибка здесь тихая: карточка, окрашенная по
случайному числу, выглядит как настоящая тревога.

### Датчики температуры и влажности

Датчик показывает измерения крупными цифрами, а всё, что можно настроить,
убирает в окно «Настройки». На стене нужны именно показания — уставки и
чувствительность трогают раз в сезон.

```
┌──────────────────────────┐        ┌────────────────────────────────┐
│ Душевая                  │        │ T & H Sensor           ●онлайн │
│ 10.5 °C                  │        │ 11.0 °C   ВЛАЖНОСТЬ            │
│ ⚙ НАСТРОЙКИ              │        │           52 %                 │
└──────────────────────────┘        │ ⚙ НАСТРОЙКИ                    │
   только температура                └────────────────────────────────┘
                                        температура и влажность
```

**Пара цифр.** Если сенсор меряет и температуру, и влажность, на карточке видно
обе: температура крупно, влажность рядом, на шаг меньше, с подписью. Раньше
влажность пряталась за кнопкой, и карточка отвечала только на половину вопроса,
с которым к ней подходят.

Правило общее, а не про это устройство: подписи `humidity_value` (thing model),
`va_humidity` и `humidity` — одна и та же величина, а уставки
`maxhum_set`/`minihum_set` в неё не попадают, потому что сравнение идёт по коду,
а не по единице `%`.

Отбор величин лежит в `web/static/figures.js` и покрыт тестами
(`make web-test`), потому что ошибиться здесь легко и незаметно. Первый вариант
исключал влажность из окна настроек, но не рисовал её — и у устройства, которое
отдаёт влажность без температуры (увлажнитель в демо-доме), значение исчезало из
интерфейса целиком. Поэтому «нарисовано» и «исключено из настроек» считает один
и тот же вызов: разойтись они теперь не могут.

Необъявленное значение показывается прочерком, не нулём: точка, объявленная в
модели, но ещё не присланная, приходит как `null`, а `Number(null)` — это `0`,
и на стене стояло бы правдоподобное «Влажность 0 %».

На узком виджете (одна колонка пульта) пара переносится на вторую строку, а не
сжимается: цифры должны остаться читаемыми с другого конца комнаты.

Настройки открываются в **модальном окне**, а не в выпадающей панели внутри
карточки. Причина техническая: панель с `position: absolute` не может подняться
выше соседних карточек — они идут позже в потоке и перекрывают её, из-за чего она
выглядела полупрозрачной. Модальное окно (`<dialog>` + `showModal`) рисуется
поверх всего, держит фокус, закрывается по Esc, по крестику и по клику на фон.

Что стоит знать:

- Сенсором считается только точка `temp_current` / `va_temperature`. Проверять
  по единице нельзя: уставки (`maxtemp_set`, `upper_temp`) приходят в тех же
  `℃`, и такой виджет продублировал бы один контрол дважды — цифрой и
  слайдером. Влажность ищется по трём кодам так же точно — `humidity_value`,
  `va_humidity`, `humidity`.
- Показанные цифрой величины уходят из окна настроек: иначе одно и то же
  значение стояло бы на карточке и строкой в списке под ней.
- Фаренгейтовые дубли (`temp_current_f`) не показываются ни в виджете, ни в
  панели.
- Единица нормализуется: `℃`, `°C` и `摄氏度` → `°C`.
- Окно переживает автообновление раз в 8 секунд: его состояние помнится в
  `state.sheet`, и пришедшие данные перерисовывают содержимое, а не закрывают
  окно под пальцем.
- Команды из окна идут теми же обработчиками, что и с пульта: переключатели,
  слайдеры и enum работают одинаково.
- Если у устройства нет записываемых функций (чистый датчик с батареей),
  панели не будет вовсе.

Добавляются такие виджеты там же, где остальные: в редакторе они идут первыми,
с подписью «Температура».

**Сенсор выглядит так и без пульта.** Если раскладка не настроена, главный экран
показывает обычные карточки — и устройство с измеряемой температурой в них тоже
рисуется крупной цифрой с панелью «Настройки», а не списком слайдеров. Раньше
сенсорный вид включался только для виджета, добавленного вручную, и датчик на
обычном экране оставался прежним.

### Вид на планшете

- Сетка вместо списка: колонки подстраиваются под ширину, на планшете — крупнее.
- Крупные цели нажатия: переключатель 4.6×2.6 rem, кнопка сцены не ниже 3.4 rem.
- Шапка прилипает к верху при прокрутке (на широком экране).
- Если устройство из раскладки исчезло (убрали лампу, выключили сцены), виджет
  остаётся на месте с пометкой «контрол недоступен» — пульт не «прыгает», и
  видно, что именно сломалось.

### Правка интерфейса

`web/static/*` и шаблон встраиваются в бинарник через `go:embed`, поэтому после
изменения `app.js` или `styles.css` сервер нужно **перезапустить** — он не
перечитывает файлы с диска.

**Страница обновляется сама.** Пульта на стене никто не перезагружает неделями, а
опрос раз в 8 секунд тянет только данные: код в открытой вкладке остаётся тем,
что был загружен. Поэтому сервер считает отпечаток встроенного бандла (хеш всех
файлов `web/`), кладёт его в `<meta name="coolhome-build">` и отдаёт в каждом
снимке (`build` в `/api/devices`). Страница, чей отпечаток разошёлся с серверным,
перезагружается сама — но не посреди правки пульта: пока открыт редактор или окно
настроек, перезагрузка ждёт следующего опроса. Без этого исправленная карточка
продолжала бы выглядеть сломанной до ручного Ctrl+F5, и отличить это от
неприменённой правки было невозможно.

**Статика отдаётся с валидатором.** Раньше файлы уходили без `ETag` и
`Cache-Control` — у встроенных файлов нет даты изменения, поэтому `http.FileServer`
не мог их прислать. Теперь каждый файл получает `ETag` по своему содержимому и
`Cache-Control: no-cache`: браузер вправе хранить копию, но обязан спросить, и
обычный ответ — `304` без тела. HTML-оболочка уходит с `no-store`: она
перечисляет скрипты, и её устаревшая копия потянула бы старый список.

### Обновление данных

Состояние по-прежнему обновляется раз в 8 секунд. Для настенного пульта это
можно замедлить, если сервер далеко: `COOLHOME_POLL_INTERVAL` влияет на опрос
облака, а интервал обновления страницы задан константой `REFRESH_MS` в
`web/static/app.js`.

## Команды отклоняются: квота облака

Симптом: устройство онлайн, карточка показывает состояние, но переключатель
возвращается назад, а в ответе на команду приходит

```
tuya api error 60001001: Your controllable device pool quota is insufficient
```

Это **не сбой CoolHome и не поломка устройства**. У Cloud-проекта Tuya есть
квота на число управляемых устройств, зависящая от тарифа. Устройства за её
пределом видны и читаются, но команды для них облако отклоняет. На вашем доме
это задело «Smart plug 2», «люстру», «1 floor temperature» и ещё часть
устройств, тогда как «Душевая» и «T & H Sensor» принимали запись в том же
прогоне — то есть квота распределена по устройствам, а не сломана целиком.

Проверить, какие устройства управляемы, можно по ответу API:

```bash
# записывается текущее значение, поэтому ничего не меняется
curl -s -X POST http://127.0.0.1:8080/api/devices/<id>/commands \
  -H 'Content-Type: application/json' \
  -d '{"commands":[{"code":"switch_1","value":false}]}'
# 200 — управляемо, 502 с code=quota_exhausted — за квотой
```

**Что делает CoolHome.** Ошибку квоты он показывает **модальным окном**, а не
баннером: это условие, которое не исчезнет само, и у него есть адрес, куда идти.

```
┌──────────────────────────────────────────────────┐
│ Облако Tuya не принимает команду              ✕  │
│                                                  │
│ У проекта Tuya исчерпана квота управляемых        │
│ устройств: облако отвечает 60001001 и отклоняет   │
│ команды для устройств за её пределами…            │
│                                                  │
│      [ Открыть консоль Tuya ↗ ]                  │
│                                                  │
│ ☐ Больше не показывать в этой сессии   [Понятно]  │
└──────────────────────────────────────────────────┘
```

- Текст называет причину, код облака и место, где её снимать
  (`Cloud → Development → ваш проект`), и прямо говорит, что устройство и
  CoolHome ни при чём.
- **Ссылка** ведёт в консоль Tuya — она открывается в новой вкладке
  (`target="_blank"`, `rel="noopener noreferrer"`). Адрес задаётся переменной
  `COOLHOME_CONSOLE_URL`, по умолчанию `https://iot.tuya.com/cloud`. Именно
  консоль, а не отдельная страница тарифа: стабильного публичного адреса у
  страницы смены плана нет — `iot.tuya.com/pricing` и подобные отдают ту же
  оболочку, что и остальные пути, так что ссылка на них была бы догадкой.
  В консоли проект и его квота видны сразу.
- **Ссылка проверяется на сервере** (`validateConsoleURL`): принимаются только
  `http` и `https` с хостом. `javascript:` или `data:` в конфиге отклонил бы
  запуск — иначе настройка превращалась бы в способ выполнить скрипт на
  странице.
- **«Больше не показывать в этой сессии»** убирает модальное окно для этого
  кода, но не саму проблему: сообщение остаётся тихим баннером. Настройка живёт
  до перезагрузки страницы намеренно — завтра квота всё ещё может быть
  исчерпана, и молчать о ней было бы хуже, чем показать снова.
- API отвечает `502` с целым сообщением:
  `{"code":"quota_exhausted", "title":"…", "message":"…", "link":"…", "link_label":"…"}`,
  а текст дублируется в `error` для клиентов, которые знают только старое поле.
  Данные для ссылки приходят с сервера, поэтому страница не хранит адресов
  консоли в коде.

**Что делать.** Увеличить квоту в консоли Tuya (тариф проекта) — после этого
команды начнут проходить без изменений в CoolHome. Убрать устройства из проекта
или снять с них управление тоже помогает, если менять тариф не хочется.

Сообщение снимается само после первой успешной команды: показывать «квота
исчерпана», когда облако уже принимает запись, было бы неправдой.

## Правила: условие → действие

Третья вкладка — автоматика. Правило смотрит на показания, которые CoolHome и
так опрашивает, и, когда они совпадают с условием, отправляет команды тем же
проверенным путём, что и нажатие на карточке: та же валидация по thing model, тот
же кэш, никакого второго способа писать в облако.

```
Правило «Холодно в спальне»          группа ОТОПЛЕНИЕ
если Датчик климата в спальне · Температура меньше 18
Кофемашина · Питание → вкл
не чаще 10m
```

**Два вида триггера, один механизм.** Условие (`when`) сравнивает показание;
расписание (`at`) — это окно местного времени. Расписание, заданное без условий,
и есть триггер по времени: «в 7:30» — это окно длиной в минуту, а срабатывание
происходит на входе в него. Расписание вместе с условиями — это ограничение:
«если холодно **и** ночь». Один и тот же код, две записи.

**Ночное окно принадлежит дню, когда оно открылось.** `22:00–06:00` с днями
`["fri"]` — это одна ночь с пятницы на субботу: суббота 02:00 относится к
пятничному окну, а пятница 02:00 — к четверговому. Проверка «какой сегодня день»
для второй половины ночи останавливала правило в полночь.

**Срабатывание на переходе, а не на каждом опросе.** По умолчанию (`edge`)
правило срабатывает один раз, когда условие стало истинным. Иначе правило
«включить обогрев, когда холодно» отправляло бы команду каждые десять секунд,
пока в комнате холодно. Режим `level` («повторять, пока верно») нужен там, где
устройство может выйти из нужного состояния само, и ограничен `cooldown`.

**Чего механизм не делает специально:**

- **Не действует на первом такте после старта.** Первая проверка только
  запоминает состояние. Иначе после перезапуска сервера все правила, чьи условия
  случайно истинны, выстрелили бы разом. Правило, уже истинное при старте, ждёт
  следующего настоящего перехода — в том числе и при заданном `for`: «условие
  держалось, пока сервер лежал» верно, но непроверяемо, и обогрев включался бы при
  каждом перезапуске. Исключение — `level`: его задача поддерживать состояние,
  поэтому он применяется на следующем такте.
- **Не молчит, если правило нельзя вычислить.** Оператор, не применимый к
  значению (`>` на enum), или десятичная запятая, попавшая в текст, раньше давали
  «условие ложно» навсегда: правило выглядело включённым и не делало ничего. Теперь
  причина попадает в строку состояния и в журнал.
- **Не считает отсутствие значения за «ложь».** Если датчик офлайн или показание
  ещё не пришло, условие «неизвестно»: правило не срабатывает и не сбрасывает
  фронт. Разрыв связи не должен выглядеть как «потеплело».
- **Не отправляет команду, которая ничего не меняет.** Если устройство уже в
  нужном состоянии, действие записывается в журнал как «уже так», но в облако не
  уходит. Без этого правило в режиме `level` тратило бы запросы впустую.
- **Бюджет такта считает записи, а не действия.** «Уже так» и отказ облака стоят
  ноль, иначе одно правило-пустышка с шестью действиями съедало бы бюджет у всех,
  кто после него. Правило, которое бюджет не пустил, сохраняет свой ход: отметка о
  срабатывании снимается, и на следующем такте оно сработает.
- **Не подтверждает вслепую.** `for` («держать 5m») требует, чтобы условие было
  истинно непрерывно; дребезг вокруг порога сбрасывает отсчёт, а не накапливает.

**Группы и выключатели.** У каждого правила есть свой переключатель, и у группы —
тоже. Это и есть ответ на «автоматика мне мешает»: человек не борется с правилом,
он его выключает — одним нажатием, с телефона, из списка. Выключение группы не
трогает выключатели её правил, поэтому включение обратно восстанавливает ровно
тот набор, который работал.

**Расписание читается в местном времени.** Часовой пояс задаётся `COOLHOME_TZ`
(имя зоны IANA, например `Europe/Moscow`); без него берётся зона машины. Окно
может переходить через полночь: `22:00–06:00` истинно с 22:00 до 23:59 и с 00:00
до 06:00.

**Журнал.** Последние 50 срабатываний: время, правило, что отправлено и что
ответило облако. Отказ (`60001001`, квота) попадает туда же текстом — иначе
правило молча не работало бы.

**«Проверить сейчас»** показывает, что сработало бы в этот момент, и **ничего не
отправляет**: ждать следующего такта, чтобы узнать, правильно ли написано
правило, — плохой способ его писать, а проверять порог не должно включать
отопление.

### Файл правил

`COOLHOME_RULES_FILE`, формат:

```json
{
  "groups": [ { "name": "Отопление", "enabled": true } ],
  "rules": [
    {
      "id": "cold-bedroom",
      "name": "Холодно в спальне",
      "group": "Отопление",
      "enabled": true,
      "when": [ { "device": "bfb7dc…", "code": "temp_current", "op": "<", "value": 180 } ],
      "for": "5m",
      "cooldown": "10m",
      "mode": "edge",
      "actions": [ { "kind": "command", "device": "bf…", "code": "switch_1", "value": true } ]
    }
  ]
}
```

- `op` — `<`, `<=`, `>`, `>=`, `==`, `!=`; числа сравниваются числами, строки —
  текстом (это нужно для enum вроде `battery_state`);
- `at` — `{ "from": "07:30", "to": "22:00", "days": ["mon","fri"] }`;
- `actions[].kind` — `command` (устройство и код) или `scene` (id сцены);
- `mode` — `edge` (по умолчанию) или `level`;
- пределы: 100 правил, 20 групп, 8 условий, 6 действий на правило, 60 символов в
  названии.

Запись атомарная, правка — под одной блокировкой (`Store.Update`), а страница
правит **одно правило одним запросом** (`PUT /api/rules/{id}`), а не весь набор.
Это не педантизм: набор целиком у каждого экрана свой, отстающий на один опрос, и
сохранение формы с планшета возвращало бы группу, которую только что выключили с
телефона. `PUT /api/rules` (весь набор) остался для скриптов.

Файл, в котором правило ссылается на удалённую группу, читается, а не падает:
ссылка отбрасывается, правило продолжает работать без группы. Запись при этом
остаётся строгой — новое правило с несуществующей группой отклоняется.

### API правил

- `GET /api/rules` — набор, состояние движка (`running`, `primed`, `last_run`),
  журнал и часовой пояс.
- `PUT /api/rules` — сохранить набор целиком (`400` при некорректном).
- `PUT /api/rules/{id}` — сохранить одно правило (создать или изменить), не
  трогая остальные.
- `DELETE /api/rules/{id}` — удалить одно правило.
- `POST /api/rules/{id}/enabled` — `{"enabled":false}`; отдельно от сохранения,
  потому что это действие «остановить сейчас».
- `POST /api/rules/groups/{name}/enabled` — то же для группы.
- `POST /api/rules/check` — что сработало бы сейчас, без отправки команд.
- `GET /api/scenes` — сцены с их действиями и признаком `editable`: `false` значит
  «облако не отдаёт содержимое, редактировать нельзя», и в `reason` написано
  почему.
- `POST /api/scenes` — создать сцену: `{"name":"…","actions":[{"device":"…","code":"…","value":…}]}`.
- `PUT /api/scenes/{id}` — изменить имя и действия устройств; остальное в сцене
  сохраняется.
- `PUT /api/scenes/{id}/enabled` — включить или выключить сцену.

### Что проверено

- ядро (`Evaluate`) — табличными тестами без сети и без часов: фронт против
  повторов, `for` и его перезапуск при дребезге, `cooldown`, режим `level`,
  отсутствующее показание, выключенное правило, выключенная группа, неизвестная
  группа, окно расписания и переход через полночь, дни недели, сравнения чисел и
  enum, отказ `>` на тексте;
- раннер — на подставном исполнителе: первый такт не действует, срабатывание по
  изменению, пропуск команды «уже так», отказ одного действия не мешает
  остальным, бюджет такта, сцены, выключение на ходу;
- хранилище — атомарная запись, отказ на некорректном наборе без порчи файла,
  копия при чтении, конкурентные обновления под `-race`;
- API — сохранение и выдача, отказы `400`, выключатели правила и группы, `404` на
  неизвестный id, dry-run действительно ничего не отправляет;
- в браузере на demo-доме: создание правила через форму (условие и действие),
  список с выключателями, группа, журнал, «Проверить сейчас», сохранение в файл.

## Безопасность

- По умолчанию слушается только `127.0.0.1`.
- Для выхода в сеть задайте `COOLHOME_AUTH_TOKEN` и помните: токен защищает API,
  а не транспорт — снаружи ставьте TLS-прокси (Caddy, nginx) или VPN.
- UI защищён CSP без inline-скриптов; все строки из Tuya экранируются.

## Что проверено, а что нет

Покрыто тестами и проверено запуском:

- подпись запросов (HMAC-SHA256 по канонической строке, RFC-вектор),
- выдача, кэширование, обновление по истечении и повтор после `1010`,
- разбор ошибок облака (включая `code` строкой), разбор `values` thing model,
- валидация команд, кэш и обновление после записи,
- HTTP-контракт, коды ошибок, auth, статика, CSP,
- CORS: preflight без токена, allowlist, отказ чужому origin, wildcard, WARN,
- раскладка пульта: валидация, атомарная запись, пустой и битый файл, конкурентный
  доступ под `-race`, API `GET/PUT`, правка на месте (добавление, удаление,
  порядок, ширина) и клик по виджету в браузере,
- компактная карточка розетки и выключателя: выбор устройств (диммер и термостат
  сохраняют полный набор), двухклавишный с независимыми клавишами и порядком из
  облака, состояние «вкл/выкл», переключатель и переход в настройки,
- отказ по квоте облака (`60001001`): распознаётся отдельно от ошибки значения,
  объясняется в терминах тарифа, показывается модальным окном со ссылкой в
  консоль, снимается успешной командой, закрывается и запоминает «не показывать»
  до перезагрузки страницы,
- ссылка на консоль: `http`/`https` обязательны, `javascript:`/`data:`/путь без
  схемы отклоняются (иначе настройка стала бы способом выполнить скрипт),
- правила: движок (edge/level, for, cooldown, расписание, группы, отсутствующее
  показание), раннер (baseline, бюджет, идемпотентность, журнал), хранилище,
  API и выключатели правила/группы, dry-run без отправки команд,
- описания сцен: хранение, обрезка и предел 280, сохранение и очистка, копия
  при чтении, имя и описание одним запросом, карточка сцены без «Настроек» с
  описанием и кнопкой правки (проверено в браузере на живом доме),
- редактор сцен: сборка документа в форме, которую облако требует
  (`space_id → name → type → actions`), отказ на неизвестное устройство, функцию
  вне thing model, значение вне диапазона и сцену внутри сцены; сохранение
  ИК-действий и порядка; отказ редактировать сцену, которую облако не отдаёт
  (40003007); переключение статуса целым документом; переименование сцены, у
  которой все действия фиксированные; отказ оставить сцену без действий; список
  действий всегда массив, не `null` (проверено на подставном облаке в браузере:
  создание, правка, показ ИК-действия, окно «нельзя изменить»; на живом аккаунте
  — только чтение: 19 сцен, 7 с фиксированными действиями, ни одного `null`),
- правка панели отдельной кнопкой в панели: включение и выключение, добавление и
  удаление карточки, независимость от сетки (в режиме правки панели сетка не
  становится редактором пульта), доступ по `?edit=1`, вход «＋ Панель» при пустой
  панели (проверено в браузере на живом доме, 420 и 1180 px),
- группы устройств: порядок полосы (избранное → группы → все), устройство не
  более чем в одной группе, перенос не копирует, удаление группы оставляет
  устройства в доме, отказ на дубликат имени и на устройство в двух группах,
  избранное сквозное и по умолчанию открыто (проверено в браузере на живом доме:
  создание группы, перенос устройства, избранное, удаление группы, 420 и 1180 px),
- батарея: предпочтение `battery_state` процентам, пороги процентов, отказ от

  четыре карточки окрашены, здоровая — нет),
- скрытие сцен: хранение и возврат, отказ на дубликат и пустой id, копия при

Не проверялось вживую: записи команд на реальные устройства и экзотические
варианты thing model (enum-режимы, `raw`) — это покрыто тестами на стабах
облака. Бандл MiniApp не открывался в Tuya IDE: проверены JSON-манифесты,
синтаксис JS и вся логика под заглушкой рантайма, но рендер `tyml` и
поведение реального `ty.request` — за вами. Проверено на живом аккаунте (`eu`): выдача токена, список из 51
устройства, статусы, `/api/health`, автоматический подбор uid при `1106`.

Подпись реализована по документации Tuya и проверяется тестом с независимым
пересчётом; при первом запуске с настоящими ключами смотрите лог:
`1004` — неверный регион или ключи; `2009` на спеку устройства — у продукта нет
старой thing model, клиент возьмёт модель из IoT Core (см. **Устройства,
которых нет в старом thing model**); `1106`/`1100` — нехватка прав у проекта
(не авторизован сервис Smart Home Device Management или к проекту не привязан
аккаунт приложения).

## Ограничения и следующие шаги

- Управление идёт через облако Tuya: интернет обязателен, есть задержка и
  лимиты частоты запросов.
- ИК-пульты только **отправляют** кнопки: обратной связи по состоянию у remote
  нет, поэтому CoolHome не знает, включился ли телевизор или свет. У
  RF-выключателя в облаке вообще один ключ `one_on` — ни `off`, ни состояния. Локальный протокол (порт 6668, `localKey`, AES)
  можно добавить вторым провайдером — интерфейс `home.Provider` уже отделён.
- Нет групп устройств, истории и уведомлений.
- Нет встроенной аутентификации пользователей: один дом, один токен.
