# CoolHome

Веб-приложение на Go для управления устройствами умного дома Tuya со своего
сервера: список устройств, живые показания, переключатели, слайдеры и
enum-режимы — в одном самодостаточном бинарнике без внешних зависимостей,
сборщиков фронтенда и базы данных.

```
cmd/coolhome        точка входа, флаги, graceful shutdown
internal/tuya       клиент Tuya Cloud OpenAPI: подпись, токен, устройства, команды
internal/home       кэш состояния, валидация команд по thing model, составной провайдер
internal/ir         ИК-пульты как устройства с кнопками (Tuya IR Control)
internal/scene      tap-to-run сцены как кнопки (Scene Linkage Rules)
internal/dashboard  раскладка пульта: какие контролы показывать
internal/demo       фейковый дом для запуска без credentials
internal/httpapi    JSON API + встроенный дашборд + CORS
web/                шаблон, CSS, JS (embed)
web-tests/          тесты правил интерфейса (node --test)
miniapp/            бандл Tuya MiniApp (tyml/tyss), клиент к этому API
miniapp-tests/      тесты бандла (node --test)
```

## Быстрый старт без ключей Tuya

```bash
make demo          # или: go run ./cmd/coolhome -demo
# http://127.0.0.1:8080
```

В демо-режиме шесть устройств (лампа, розетка, термостат, датчик климата,
шторы, выключенный увлажнитель): команды меняют состояние, датчик «дышит»,
офлайн-устройство отклоняет команды — видно, как ведёт себя интерфейс.

## Подключение своего дома

1. Зарегистрируйтесь на [iot.tuya.com](https://iot.tuya.com) и создайте
   Cloud-проект (**Cloud → Development → Create Cloud Project**).
2. В проекте возьмите **Access ID** (`TUYA_CLIENT_ID`) и **Access Secret**
   (`TUYA_CLIENT_SECRET`).
3. Привяжите аккаунт приложения: **Devices → Link Tuya App Account → Add App
   Account**, отсканируйте QR-код из Smart Life / Tuya Smart (тот аккаунт, где
   уже есть ваши устройства).
4. Убедитесь, что в проекте авторизованы нужные API-сервисы (в терминах Tuya
   это **IoT Core** / **Authorization Token Management** / **Smart Home Device
   Management**; набор зависит от проекта и региона).
5. Выберите дата-центр аккаунта — `TUYA_REGION`:

```
cn    openapi.tuyacn.com            Китай
us    openapi.tuyaus.com            Западная Америка
ueaz  openapi-ueaz.tuyaus.com       Восточная Америка
eu    openapi.tuyaeu.com            Центральная Европа
weaz  openapi-weaz.tuyaeu.com       Западная Европа
in    openapi.tuyain.com            Индия
sg    openapi-sg.iotbing.com        Сингапур
```

Неверный дата-центр выглядит как `sign invalid` / `1004`. Точный хост можно
задать напрямую через `TUYA_BASE_URL`.

6. Запустите:

```bash
cp .env.example .env      # заполните TUYA_CLIENT_ID / TUYA_CLIENT_SECRET / TUYA_REGION
set -a; . ./.env; set +a
make run
```

Файл `.env` приложение не читает само — переменные окружения экспортируйте
любым привычным способом (systemd `EnvironmentFile`, docker `--env-file`, dotenv
в обёртке).

## Конфигурация

- `COOLHOME_ADDR` — адрес прослушивания, по умолчанию `127.0.0.1:8080`.
- `COOLHOME_DEMO` — `true` включает фейковый дом.
- `COOLHOME_AUTH_TOKEN` — если задан, `/api/*` требуют
  `Authorization: Bearer <токен>` (или `X-Auth-Token`).
- `COOLHOME_POLL_INTERVAL` — период опроса облака, по умолчанию `10s`.
- `COOLHOME_DEVICE_IDS` — список `device_id` через запятую, если нужен не весь дом.
- `COOLHOME_ALLOWED_ORIGINS` — CORS-политика для браузерных клиентов (например,
  Tuya MiniApp в webview): origin через запятую, только `схема://хост[:порт]`,
  без путей. По умолчанию пусто — CORS выключен, заголовки не выставляются.
  `*` открывает API любой странице — используйте только вместе с
  `COOLHOME_AUTH_TOKEN` и осознанно (при старте будет WARN).
- `TUYA_CLIENT_ID`, `TUYA_CLIENT_SECRET`, `TUYA_REGION` — доступ к облаку.
- `TUYA_UID` — uid аккаунта приложения (Smart Life / Tuya Smart), привязанного
  к проекту. Это **не** uid владельца Cloud-проекта, который приходит в ответе
  на токен: `/v1.0/users/{uid}/devices` принимает только uid привязанного
  аккаунта и на чужой отвечает `1106`. Задавать обычно не нужно — при `1106`
  клиент сам находит привязанный аккаунт через
  `/v1.0/iot-01/associated-users/devices` и запоминает uid. Переменная нужна,
  чтобы указать uid явно: тогда он используется как есть и не
  переопределяется.
- `COOLHOME_IR` — `true` включает провайдер инфракрасных пультов: remote'ы,
  сохранённые на ИК-пульте, показываются как устройства с кнопками. Требует
  подписки на сервис **IR Control** в консоли Tuya; без неё приложение работает
  как обычно и пишет одно предупреждение в лог.
- `COOLHOME_IR_BLASTERS` — `device_id` ИК-пультов через запятую. Пусто — найти
  автоматически (категория `wnykq`).
- `COOLHOME_SCENES` — `true` включает провайдер сцен: tap-to-run сцены
  показываются как устройства с одной кнопкой. Это **рабочий способ** нажать то,
  что не умеет data-point API, — сцену исполняет облако Туи.
- `COOLHOME_SPACE_ID` — id дома (`space`). Пусто — определяется автоматически.
- `COOLHOME_DASHBOARD_FILE` — файл с раскладкой пульта (см. ниже). Пусто —
  раскладка только в памяти, изменения не переживут перезапуск.
- `TUYA_BASE_URL` — переопределение endpoint.

Флаги: `-addr`, `-demo`, `-interval`.

## HTTP API

- `GET /api/devices` — снимок дома: устройства, статусы, функции с разобранными
  диапазонами (`min`, `max`, `step`, `scale`, `unit`, `options`).
- `GET /api/devices/{id}` — одно устройство.
- `POST /api/devices/{id}/commands` — запись: `{"commands":[{"code":"switch_1","value":true}]}`.
- `POST /api/refresh` — принудительное обновление из облака.
- `GET /api/health` — состояние синхронизации.
- `GET /api/dashboard` — раскладка пульта: `{"widgets":[…]}`.
- `PUT /api/dashboard` — сохранить раскладку (`400` при некорректной).

Команда проверяется по thing model устройства: неизвестный код, неверный тип,
значение вне `min..max` или вне `enum` отклоняются с `400` до обращения в облако.
Ошибка облака возвращается как `502` с текстом причины.


## Устройства без thing model

Часть устройств Tuya не описывается через data-point API: облако отвечает
`2009 not support this device`. На практике это датчики и сам ИК-пульт; в
типичном доме — 4 устройства из 51 после того, как RF-выключатели были
подхвачены провайдером ИК-пультов (см. раздел **Инфракрасные пульты**).

У RF-выключателей data-point модели тоже нет, но управлять ими всё-таки можно —
через ИК-пульт, а не через DP. Если у вас такие устройства показываются как
«нет функций», проверьте `COOLHOME_IR=true`.

Такие устройства не сломаны и не «недопривязаны»: у них просто нет thing model,
поэтому у них нет ни функций, ни статуса. Запрос в облако этого не изменит.

Как это обрабатывается:

- `tuya.IsUnsupportedDevice(err)` отличает `2009` от остальных ошибок;
- сервис помечает такое устройство `SpecUnsupported` (в JSON —
  `spec_unsupported: true`) и кэширует ответ на **24 часа**, а не на 2 минуты:
  иначе каждый опрос заново спрашивал бы облако про каждый RF-выключатель;
- в API такое устройство приходит с пустыми `functions` и `readings`;
- UI показывает объяснение по категории, а не текст ошибки, — иначе интеграция
  выглядит сломанной. Причина у разных устройств разная, поэтому и текст разный:
  для RF-выключателя (`rf_switch1`) — что им управляют с физического пульта, для
  самого ИК-пульта (`wnykq`) — что его пульты открываются через `COOLHOME_IR`,
  для датчиков и термометров — что Tuya Cloud просто не отдаёт их через API.
  Одна общая фраза «управляется своим пультом» была бы неверна для датчика.

Управлять таким устройством через CoolHome сейчас нельзя: у него нет
data-point модели. Единственный путь — сервис **IR Control** в проекте Tuya
(`/v1.0/infrareds/...`); без подписки на него облако отвечает
`28841101 No permissions. This API is not subscribed`. Это отдельная
поверхность провайдера (список пультов → кнопки → отправка), и она не входит
в текущую реализацию.

## Инфракрасные пульты

ИК-пульт (`wnykq`) — это отдельная поверхность облака: у него есть remote'ы
(телевизор, кондиционер, гирлянда), а у каждого remote'а — кнопки. Кнопка это
действие, а не состояние, поэтому CoolHome показывает remote как устройство,
у которого все функции — кнопки: запись `true` нажимает кнопку.

Включается через `COOLHOME_IR=true`. Провайдер (`internal/ir`) отдаёт remote'ы в
том же интерфейсе, что и физические устройства, а `home.Multi` склеивает два
провайдера: основной дом и дополнительную поверхность.

```
GET  /v1.0/infrareds/{blaster}/remotes                        библиотечные remote'ы
GET  /v1.0/devices/{blaster}/sub-devices                      выученные remote'ы
GET  /v1.0/infrareds/{blaster}/remotes/{remote_id}/keys       кнопки
GET  /v1.0/infrareds/{blaster}/remotes/{remote_id}/learning-codes  выученные коды
POST /v1.0/infrareds/{blaster}/remotes/{remote_id}/command        нажать библиотечную кнопку
POST /v1.0/infrareds/{blaster}/remotes/{remote_id}/learning-codes передать выученный код
GET  /v1.0/infrareds/{blaster}/categories                     категории
```

**Библиотечные и выученные клавиши — принципиально разные вещи.**

- **библиотечная клавиша** (`standard_key: true`, например `PowerOn` у
  кондиционера) — настоящая кнопка: `POST .../remotes/{id}/command`
  с `{"key":"PowerOn"}`. Работает.
- **выученная клавиша** (`standard_key: false`, все RF-выключатели, у них одна
  клавиша `one_on`) — **облако не передаёт её вообще**. Проверено со всех
  сторон:

  | попытка | ответ облака |
  |---|---|
  | `POST .../command {"key":"one_on"}` | `30706 command or value not support` |
  | `POST .../command {"key":12}` | `30706` |
  | `POST .../learning-codes {"code":"<выученный код>"}` | `success: true`, но в эфир ничего не уходит |
  | `POST .../commands {"code":"ir_send",...}` | `2008 command or value not support` |
  | `PUT .../properties`, `v2.0/cloud/thing/...` | `1108 uri path invalid` |

  Ключевое доказательство по `learning-codes`: запрос возвращает `success`, но
  data point `ir_send` блэстера **не меняется** (его `time` остаётся на дате
  реальной передачи в январе), а `active_time` выключателя не обновляется.
  То есть это «отправить код в режиме обучения», а не рабочая передача.

Поэтому такие клавиши отдаются с типом `Passive`, а не `Button`: устройство
видно, у него перечислены настоящие кнопки, но запись отклоняется с `400` и
объяснением, а в интерфейсе выводится заметка. Кнопка, которая молча не
работает, хуже отсутствующей кнопки.

**Как всё-таки управлять RF-выключателями — через сцены.** Облако не передаёт
выученный RF-код по запросу, но **исполняет сцену**, в которой этот код
записан. Это рабочий путь, и он включён: `COOLHOME_SCENES=true`.

```
GET  /v2.0/cloud/scene/rule?page_no=1&page_size=50&space_id={space}&type=scene
POST /v2.0/cloud/scene/rule/{rule_id}/actions/trigger
```

Сервис называется **Scene Linkage Rules** (старый `Smart Home Scene Linkage`
помечен legacy). Проверено на живом доме: 19 сцен приходят списком, а
`trigger` реально выполняется — облако различает существующую сцену (успех) и
несуществующую (`40003900 No linkage permissions`), то есть вызов доходит до
исполнения.

Две детали этого API:

- **`space_id` обязателен** и берётся только из `/v2.0/cloud/thing/{id}`
  (`bind_space_id`) — в списке `/v1.0/users/{uid}/devices` его нет.
- **Параметры query должны идти по алфавиту**: облако подписывает
  каноническую строку, и другой порядок даёт `1004 sign invalid`. `url.Values.Encode`
  сортирует сам, поэтому клиент корректен.

**Когда сцены включены, RF-выключатели показываются только сценами.**
`COOLHOME_SCENES=true` убирает дубль: и физическую запись `rf_switch1` (у неё нет
data-point модели), и выученный remote из IR-провайдера. Остаётся одна карточка —
сцена, и она работает.

Что при этом **не** скрывается:

- библиотечные пульты (`Кондер` с клавишами `PowerOn`/`T`/…): у них есть рабочие
  кнопки, сцены их не заменяют;
- датчики и сам ИК-пульт: сцены их не покрывают, поэтому они остаются видимыми с
  объяснением, почему через API ничего не отдают.

На типичном доме это 62 устройства вместо 70: 19 сцен, 1 библиотечный пульт,
остальное — физические устройства.

Ограничение: сцена — это действие, а не состояние. CoolHome не знает, включился
ли свет, и одна и та же сцена «вкл/выкл» работает как переключатель.

**Главное открытие: RF-выключатели не видны в `/remotes`.** Они приходят только
как sub-устройства пульта (`/devices/{blaster}/sub-devices`), хотя команды им
отправляются по тому же пути `/remotes/{remote_id}/command`. Провайдер
объединяет оба списка и убирает дубли: без этого восемь RF-выключателей home
показывались как «нет функций». Именно так «Второй этаж», «Лестница»,
«Кухня свет» и остальные получили кнопку.

Две детали этого API стоят отдельного упоминания, потому что обе выглядят как
чужие ошибки:

- **Адресация по `remote_id`, не по `remote_index`.** По индексу облако
  отвечает `1106 permission deny` — выглядит как проблема прав, а на деле
  неверный идентификатор.
- **Ответы — массивы**, а числа в них — строки (`"category_id":"5"`,
  `"remote_index":"449101998"`). Список кнопок завёрнут в объект с `key_list`,
  а `key_id` в реальной библиотеке всегда `0`, поэтому кнопка адресуется
  строкой `key`.

Что важно в поведении:

- **Дополнительная поверхность не ломает основной дом.** Если сервис не
  подписан (облако отвечает `28841101 No permissions. This API is not
  subscribed`), провайдер один раз пишет предупреждение с точной подсказкой,
  где подписаться, и дальше молчит. Список устройств остаётся полным,
  `/api/health` остаётся `ok`.
- **Remote не дублирует своё устройство.** `remote_id` в облаке совпадает с
  `device_id` этого remote'а в списке устройств, поэтому провайдер отдаёт id
  как есть, а составной провайдер заменяет пустую карточку версией с кнопками.
- **Маршрутизация по владению, а не по префиксу.** `home.Multi` запоминает,
  какой провайдер отдал какой `device_id` при последнем опросе, поэтому запрос
  к remote'у не тратится на физический дом и наоборот.
- **Кнопки имеют домен.** Записывать можно только `true` («нажать»); `false`,
  строка или число отклоняются с `400` до обращения в облако — иначе значение
  слайдера ушло бы как нажатие клавиши.
- **Клавиши кэшируются** на 30 минут: они меняются только когда remote правят в
  приложении Tuya. Список пультов ищется один раз за процесс.

Кнопка отрисована и в веб-UI (`.press`, событие `press`), и в бандле MiniApp
(`onPress`).

### Что здесь проверено

Проверено на живом облаке после подписки на IR Control:

- список remote'ов, категорий и sub-устройств разбирается в реальные структуры;
- ключи читаются из `key_list`, а у выученных remote'ов — по одному ключу `one_on`;
- адресация по `remote_index` действительно даёт `1106`, по `remote_id` — работает;
- на несуществующий ключ облако отвечает `30706 command or value not support`
  и для библиотечного remote'а, и для RF-выключателя — то есть путь команды и
  форма тела верны в обоих случаях;
- на реальном доме: 51 устройство, без дублей; «Кондер» — библиотечный remote с
  пятью рабочими кнопками, восемь RF-выключателей — с клавишей `one_on` и
  честной пометкой, что облако их не передаёт.

**Не проверено:** фактическое переключение кондиционера нажатием библиотечной
кнопки — это физическое действие. Путь и форма тела для неё подтверждены
ответом `30706` на несуществующую клавишу (значит запрос доходит и
разбирается).

У RF-выключателя в облаке только один ключ `one_on`: обратного `one_off` нет, и
что именно делает физический пульт (включает или переключает) не сказано нигде
в API. Поэтому подпись кнопки в UI нейтральная — «Кнопка», а не «Включить».

## Tuya MiniApp

В репозитории лежит готовый бандл — каталог [`miniapp/`](miniapp). Это нативный
проект Tuya MiniApp (`tyml`/`tyss`), который подключается к вашему серверу и
работает с домом.

```
miniapp/
  project.tuya.json   имя проекта, baseversion 2.2.0, BaseKit/TYKit/MiniKit
  app.json            страницы, окно, networkTimeout
  theme.json          светлая и тёмная темы через @-переменные
  app.js, app.tyss    точка входа и общие стили
  utils/api.js        транспорт и клиент CoolHome: настройки, /api/*
  utils/format.js     scale и значения: показ и обратное кодирование
  utils/view.js       view-модели: карточка, показания, виджеты
  pages/home/         подключение к серверу и список устройств
  pages/device/       управление: switch, slider, picker, показания
```

Что делает бандл:

- при первом запуске спрашивает адрес сервера и токен и проверяет их через
  `/api/health`; сохраняет в `ty.setStorageSync` только если сервер ответил
  или если он ответил `5xx` — это значит «сервер есть, но его облако не в
  порядке» (неверные ключи, чужой регион, сбой), и такой случай показывается
  баннером на главном экране, а не блокирует сохранение; `401` и сетевые
  ошибки сохранение блокируют;
- список устройств: иконка по категории, превью показаний, отметка «офлайн»,
  pull-to-refresh;
- страница устройства: переключатели для `Boolean`, слайдеры для числовых
  точек с диапазоном, `picker` для `enum`; запись идёт через
  `POST .../commands` с последующей перезагрузкой, поэтому на экране
  оказывается принятое облаком значение, а не нажатие;
- `scale` учтён в обе стороны: сырое `235` показывается как `23.5 °C`, а
  обратно отправляется целым `235` — именно этого требует Tuya;
- точки без диапазона и без `options` не превращаются в виджет, который всё
  равно не сможет отправить значение;
- на офлайн-устройстве команда не отправляется вовсе — показывается
  предупреждение;
- ошибки выводятся текстом: `400` — отказ валидации, `401` — просьба ввести
  токен, `502` — отказ облака или офлайн.

Сборка и запуск:

1. Откройте Tuya MiniApp IDE (Tuya MiniApp Developer Tool).
2. Импортируйте каталог `miniapp/` как проект.
3. Соберите и откройте в симуляторе или в приложении Smart Life.
4. Введите адрес своего CoolHome (публичный HTTPS) и токен доступа.

Проверить логику без IDE можно локально:

```bash
make miniapp-test     # хелперы, клиент и обработчики страниц
make check-all        # то же плюс gofmt/vet/go test
```

Тесты гоняют настоящие страницы и клиент против живого сервера в demo-режиме.
Заглушка `ty` повторяет контракт рантайма (колбеки `request`, синхронный
`storage`), поэтому проверены реальные `onLoad`, `onTap`, `onToggle`,
`onSlide`, `onPick`, а не только чистые функции. Отдельные сценарии со
сбоями (отказ облака, обрыв сети, посторонний сервер по адресу, запись в
полёте) идут на скриптованном рантайме — иначе они зависели бы от того, что
предыдущие тесты сделали с демо-домом.

Каждый такой тест проверен на обратимость: если откатить исправление, он
падает. Это относится и к привязке `disabled` в `tyml` — её читает отдельный
тест по шаблону, потому что JS-тесты шаблон не видят.

### Что должен подтвердить ваш проект

- **Доступ к внешнему домену.** В опубликованных типах рантайма
  (`@tuya-miniapp/api-types`) объявлен только `ty.requestCloud` — прокси к API
  Туи по имени метода, а не произвольный URL. При этом в `app.json` шаблона
  есть `networkTimeout.request`, а рантайм повторяет WeChat-контракт (`ty.*`,
  wx-совместимые вызовы). Сетевой слой бандла изолирован в
  `miniapp/utils/api.js`: он берёт `ty.request`, иначе `wx.request`, и падает
  с понятной ошибкой, если нет ни того, ни другого. Если в вашей консоли
  внешние домены запрещены — добавьте домен CoolHome в allowlist проекта.
- **Origin для CORS.** Если рантайм делает нативный запрос, заголовка `Origin`
  нет и CORS не участвует. Если запрос идёт из webview через fetch, сервер
  должен разрешить этот origin: задайте `COOLHOME_ALLOWED_ORIGINS` (фактический
  Origin видно в логе сервера или в devtools).
- **Публикация.** Панель привязывается к устройству или группе (`deviceId`,
  `groupId` в конфиге инициализации), но бандл показывает *весь дом* с сервера.
  При публикации учитывайте, что пользователь увидит все устройства аккаунта,
  а не только то, для которого открыта панель.

## Пульт на планшете

Интерфейс можно использовать как настенный пульт: открыть на планшете по web и
оставить включённым. Для этого главный экран показывает не все устройства, а
только выбранные контролы.

**Виджет — это контрол, а не карточка устройства.** Один переключатель, один
слайдер, одна кнопка сцены. На стене это удобнее карточек: шесть кнопок нужного
размера вместо шести одинаковых блоков.

### Панель «Сейчас включено»

Над сеткой есть полоса с тем, что включено прямо сейчас: имя устройства и чем
именно оно включено. Из неё видно оставленный свет, не листая карточки; нажатие
на чип открывает настройки этого устройства.

```
СЕЙЧАС ВКЛЮЧЕНО (4)
[ Душевая       ] [ Smart plug 2  ] [ Breaker       ] [ WIFI Meter Pro ]
[ ПИТАНИЕ       ] [ ПИТАНИЕ       ] [ ПИТАНИЕ       ] [ ПИТАНИЕ        ]
```

**Что считается «включено».** Правило узкое: только коды `switch`,
`switch_all`, `switch_led` и `switch_1..n`. Не любой boolean, потому что
настройки тоже boolean, и наивная проверка даёт ложные срабатывания:

- термостаты держат `upper_temp_switch` и `lower_temp_switch` в `true`
  постоянно — это включённые пороговые сигналы, а не питание. На вашем доме
  такая ошибка показала бы четыре окна и тёплых пола включёнными, хотя они
  выключены;
- у розеток есть `child_lock` и `overcharge_switch`, у Breaker —
  `switch_prepayment`, у увлажнителей — `muffling`.

Правило лежит в `web/static/power.js` и покрыто тестами (`make web-test`),
потому что ошибка здесь не косметическая: панель начала бы утверждать, что
устройство работает.

**Общий выключатель главнее реле.** У «Душевой» облако одновременно отдаёт
`switch_all = false` и `switch_1 = true`. Первая версия правила брала любой
включённый `switch_N` и показывала устройство включённым, а в настройках первый
же контрол — «Питание (всё)» — был выключен. Теперь приоритет такой:

1. есть `switch_all` — он и решает;
2. иначе есть `switch` — он;
3. иначе `switch_led`;
4. иначе независимые реле `switch_1..n`, и тогда «включено», если горит хотя бы
   одно — это верно для удлинителя без общего выключателя.

На вашем доме правило убрало из панели ещё одно устройство: было 4, стало 3.

**Офлайн-устройства не показываются.** Если устройство потеряло связь, его
последнее известное состояние может быть устаревшим: розетка могла обесточиться
вместе с роутером, и «вкл» в облаке ничего не значит. Панель отвечает на вопрос
«что работает сейчас», поэтому в неё попадают только устройства на связи.
На вашем доме это убрало два чипа из шести.

**Сцены не попадают в панель.** Сцена — действие, а не состояние: у неё нет
«включена». Придумывать её статус значило бы врать.

Панель скрыта, когда ничего не включено, и в режиме правки, где она только
мешает.

### Как настроить

Всё делается на главном экране, без отдельной страницы настроек.

1. Открыть `http://<сервер>:8080/` (или сразу `/?edit=1`).
2. Нажать **Изменить** в шапке — карточки окружаются кнопками.
3. Добавить контрол: тайл **＋ Добавить** в конце сетки → выбрать из списка →
   контрол сразу появляется на пульте.
4. Убрать: **✕** под карточкой. Порядок: **←** и **→**. Ширина: **1×/2×**.
5. Нажать **Готово**.

**Сохранение происходит сразу после каждого действия** — кнопки «Сохранить»
нет. На настенном планшете нет момента «я закончил»: человек нажимает ✕ и уходит,
и ожидает, что так и останется. Запрос уходит с задержкой 250 мс, чтобы серия
быстрых нажатий не превращалась в очередь запросов.

Пока раскладка пуста, показываются все устройства, как раньше, — существующая
установка продолжает работать без настройки. Убрать последний контрол тоже
безопасно: пульт снова превращается в общий список.

Пока идёт правка, органы управления внутри карточек не реагируют на нажатия:
иначе промах мимо **✕** переключил бы свет.

### Где хранится

На сервере, в файле `COOLHOME_DASHBOARD_FILE`:

```json
{
  "widgets": [
    { "device_id": "bf6ea99d…", "code": "switch_led", "title": "Свет", "span": 2 },
    { "device_id": "W00cRSrGbI8uKzrj", "code": "trigger", "title": "Кухня" }
  ]
}
```

- `title` — подпись на пульте (иначе берётся имя устройства);
- `span` — `1` или `2` колонки;
- порядок в массиве = порядок на экране.

Почему не `localStorage`: планшет на стене теряет кэш при обновлении браузера или
замене железа, и вместе с ним уехал бы весь пульт. Файл переживает и это, и
перезапуск сервера. Заодно один набор видят планшет и телефон.

Файл пишется атомарно (временный файл + `rename`), так что сбой посреди записи не
оставит обрезанный JSON. Раскладка читается и пишется через
`GET`/`PUT /api/dashboard`; сервер проверяет её (уникальность, обязательные поля,
предел 200 виджетов) и отвечает `400` с объяснением.

### Датчики температуры

Температурный виджет показывает измерение крупными цифрами, а всё, что можно
настроить, убирает в раскрывающуюся панель «Настройки». На стене нужен именно
показания — уставки и чувствительность трогают раз в сезон.

```
┌───────────────────┐
│ Душевая           │
│ 10.5 °C           │   ← измерение: 2.6–3.6 rem, monospaced digits
│ ⚙ НАСТРОЙКИ       │   ← открывает модальное окно
└───────────────────┘
```

Настройки открываются в **модальном окне**, а не в выпадающей панели внутри
карточки. Причина техническая: панель с `position: absolute` не может подняться
выше соседних карточек — они идут позже в потоке и перекрывают её, из-за чего она
выглядела полупрозрачной. Модальное окно (`<dialog>` + `showModal`) рисуется
поверх всего, держит фокус, закрывается по Esc, по крестику и по клику на фон.

Что стоит знать:

- Сенсором считается только точка `temp_current` / `va_temperature`. Проверять
  по единице нельзя: уставки (`maxtemp_set`, `upper_temp`) приходят в тех же
  `℃`, и такой виджет продублировал бы один контрол дважды — цифрой и
  слайдером.
- Фаренгейтовые дубли (`temp_current_f`) не показываются ни в виджете, ни в
  панели.
- Единица нормализуется: `℃`, `°C` и `摄氏度` → `°C`.
- Окно переживает автообновление раз в 8 секунд: его состояние помнится в
  `state.sheet`, и пришедшие данные перерисовывают содержимое, а не закрывают
  окно под пальцем.
- Команды из окна идут теми же обработчиками, что и с пульта: переключатели,
  слайдеры и enum работают одинаково.
- Если у устройства нет записываемых функций (чистый датчик с батареей),
  панели не будет вовсе.

Добавляются такие виджеты там же, где остальные: в редакторе они идут первыми,
с подписью «Температура».

**Сенсор выглядит так и без пульта.** Если раскладка не настроена, главный экран
показывает обычные карточки — и устройство с измеряемой температурой в них тоже
рисуется крупной цифрой с панелью «Настройки», а не списком слайдеров. Раньше
сенсорный вид включался только для виджета, добавленного вручную, и датчик на
обычном экране оставался прежним.

### Вид на планшете

- Сетка вместо списка: колонки подстраиваются под ширину, на планшете — крупнее.
- Крупные цели нажатия: переключатель 4.6×2.6 rem, кнопка сцены не ниже 3.4 rem.
- Шапка прилипает к верху при прокрутке (на широком экране).
- Если устройство из раскладки исчезло (убрали лампу, выключили сцены), виджет
  остаётся на месте с пометкой «контрол недоступен» — пульт не «прыгает», и
  видно, что именно сломалось.

### Правка интерфейса

`web/static/*` и шаблон встраиваются в бинарник через `go:embed`, поэтому после
изменения `app.js` или `styles.css` сервер нужно **перезапустить** — он не
перечитывает файлы с диска. Если после правки браузер показывает старое,
проверьте это первым делом, а не кэш браузера.

### Обновление данных

Состояние по-прежнему обновляется раз в 8 секунд. Для настенного пульта это
можно замедлить, если сервер далеко: `COOLHOME_POLL_INTERVAL` влияет на опрос
облака, а интервал обновления страницы задан константой `REFRESH_MS` в
`web/static/app.js`.

## Безопасность

- По умолчанию слушается только `127.0.0.1`.
- Для выхода в сеть задайте `COOLHOME_AUTH_TOKEN` и помните: токен защищает API,
  а не транспорт — снаружи ставьте TLS-прокси (Caddy, nginx) или VPN.
- UI защищён CSP без inline-скриптов; все строки из Tuya экранируются.

## Что проверено, а что нет

Покрыто тестами и проверено запуском:

- подпись запросов (HMAC-SHA256 по канонической строке, RFC-вектор),
- выдача, кэширование, обновление по истечении и повтор после `1010`,
- разбор ошибок облака (включая `code` строкой), разбор `values` thing model,
- валидация команд, кэш и обновление после записи,
- HTTP-контракт, коды ошибок, auth, статика, CSP,
- CORS: preflight без токена, allowlist, отказ чужому origin, wildcard, WARN,
- раскладка пульта: валидация, атомарная запись, пустой и битый файл, конкурентный
  доступ под `-race`, API `GET/PUT`, правка на месте (добавление, удаление,
  порядок, ширина) и клик по виджету в браузере,
- панель «Сейчас включено»: правило питания (настройки-булевы не считаются
  питанием), приоритет общего выключателя над реле (несогласованность панели и
  окна настроек на «Душевой»), несколько реле без общего, исключение
  офлайн-устройств, скрытие при пустом списке и в режиме правки,
- виджет-датчик: крупное значение, модальные настройки, команда из окна,
  сохранение окна при автообновлении, закрытие по Esc и фону, отсутствие дублей
  среди кандидатов редактора,
- устройства без thing model: классификация `2009`, пометка `spec_unsupported`,
  длинный TTL для постоянного ответа (и короткий — для временных ошибок),
- ИК-провайдер: remote'ы как устройства с кнопками, кэш клавиш, отключение при
  `28841101`, маршрутизация составного провайдера, валидация «только нажатие»,
- живой прогон в demo-режиме: список, команды, отказы, health,
- бандл MiniApp: `scale` в обе стороны, выбор виджета, разбор значений,
  плюс реальные обработчики страниц против живого сервера (`make miniapp-test`).

Не проверялось вживую: записи команд на реальные устройства и экзотические
варианты thing model (enum-режимы, `raw`) — это покрыто тестами на стабах
облака. Бандл MiniApp не открывался в Tuya IDE: проверены JSON-манифесты,
синтаксис JS и вся логика под заглушкой рантайма, но рендер `tyml` и
поведение реального `ty.request` — за вами. Проверено на живом аккаунте (`eu`): выдача токена, список из 51
устройства, статусы, `/api/health`, автоматический подбор uid при `1106`.

Подпись реализована по документации Tuya и проверяется тестом с независимым
пересчётом; при первом запуске с настоящими ключами смотрите лог:
`1004` — неверный регион или ключи, `2009` — недействительный Client ID,
`1106`/`1100` — нехватка прав у проекта (не авторизован сервис Smart Home
Device Management или к проекту не привязан аккаунт приложения).

## Ограничения и следующие шаги

- Управление идёт через облако Tuya: интернет обязателен, есть задержка и
  лимиты частоты запросов.
- ИК-пульты только **отправляют** кнопки: обратной связи по состоянию у remote
  нет, поэтому CoolHome не знает, включился ли телевизор или свет. У
  RF-выключателя в облаке вообще один ключ `one_on` — ни `off`, ни состояния. Локальный протокол (порт 6668, `localKey`, AES)
  можно добавить вторым провайдером — интерфейс `home.Provider` уже отделён.
- Нет сценариев, групп устройств, истории и уведомлений.
- Нет встроенной аутентификации пользователей: один дом, один токен.
